# vanda の用語

vanda の仕様（`docs/spec.md`）とコード・コメント・コミットのメッセージで使う言葉。


## やり方と約束

| 言葉 | 意味 |
|---|---|
| エビデンス・ファースト開発 | AI がソースコードを書き、人はソースコードを読まずに、約束とエビデンスで開発を進めるやり方 |
| 約束リスト | 約束・用語・機能をまとめた一覧（quenta では `spec/assurance.toml`。quenta の規則では「保証の台帳」） |
| 約束 | ソフトウェアが成り立たせると決めたこと（quenta の規則では「主張」） |
| コア機能 | 失敗すると著しい損害があるので、十分に確かめると決めた機能。約束リストの項目は `core` |
| 形式手法を使う機能 | オラクル（TLA+）で確かめる機能。約束リストの項目は `formal`。コア機能は、理由を書いて合意しない限り形式手法を使う |
| 用語 | ものや概念（例: タスク、タスクの ID）。約束の対象の 1 つ |
| 機能 | 利用者が行う操作（例: タスクの登録）。約束の対象の 1 つ |
| レイヤー | 約束がソフトウェアのどの部分の話か。モデル（判定と状態の変化）・CLI（引数と出力の形）・DB（保存） |
| 由来 | 約束が作られ・変わった履歴。1 件ごとに、ストーリーと、そのきっかけになった判断を結ぶ（「出どころ」はこれにまとめた） |

## エビデンス

| 言葉 | 意味 |
|---|---|
| エビデンス | 約束が成り立っていることの裏付け（quenta の規則では「裏付け」） |
| ステージ | エビデンスを得る開発の段階。計画・実装・テスト・リリース・運用。約束リストの項目は `stage` |
| タイプ | エビデンスの種類（オラクル、クロスチェック、シナリオなど）。約束リストの項目は `type` |
| オラクル | クロスチェックやランダムチェックの正解を出すもの。TLA+ のモデルや、証明した関数など。エビデンスのタイプではない |
| モデル検査 | エビデンスのタイプ（`model-check`）。決めた範囲の中のすべての状態をたどって、性質が成り立つことを確かめる（TLC） |
| 証明 | エビデンスのタイプ（`proof`）。すべての値で性質が成り立つことを示す（Dafny） |
| 読み下し | オラクルを自然言語に訳したもの（quenta の規則では「逆翻訳」） |
| クロスチェック | オラクルと実装に同じ操作を送り、結果を比べるテスト（モデルベーステスト）。タイプの値は `cross-check` |
| ランダムチェック | 無作為な入力で性質を確かめるテスト（プロパティベーステスト） |
| デコイテスト | わざと不具合を仕込み、テストが捕まえるかを試すもの（変異テスト） |
| キャッチしない理由 | デコイテストで、テストがキャッチしないデコイと、その理由の一覧。1 件ごとに理由の種類と文を持つ（「対象外」から改名した） |
| 等価デコイ | 仕込んでも振る舞いが変わらないデコイ（等価ミュータントにあたる）。どんなテストでもキャッチできない |
| 約束外デコイ | 約束していない振る舞いだけを変えるデコイ（例: エラーの文言）。キャッチするテストを書けるが、書かない |
| キャッチ率 | デコイテストで、仕込んだ不具合のうちテストが捕まえた割合（検出力） |
| シナリオ | CLI のコマンドの並びで約束を確かめる台本（エビデンスの本体） |
| シナリオテスト | シナリオを動かして確かめるエビデンスのタイプ（`scenario-test`。E2E テスト） |
| ガードレール | 実装のコードとは別の所で、約束に反するものを拒む仕組み。コードを読まない人が確かめられるもの。例: DB の制約・トリガー、ファイルの権限、外との境界のスキーマの検証、サンドボックスや通信の許可の一覧。見つけるだけのもの（センサー、テスト）は含めない |
| センサー | 実装のコードの中で、操作の後に約束が成り立っているかを確かめ、破れていたら見つけて知らせる仕組み（事後条件の確認）。拒むのではなく見つける。例: 操作の後の状態を確かめ、破れていればエラーを返して記録する。実装のコードの外で拒むものはガードレール、開発中に確かめるものはテスト |
| 実行の結果 | エビデンスを実行したときの、日時・版・合格したか・ログ |
| 実行の記録 | ランダムチェックとクロスチェックで、実際に流した値と結果 |

## レビューと合意

| 言葉 | 意味 |
|---|---|
| ストーリー | 開発の単位。ストーリーの置き場所（GitHub Issues など）で管理する |
| 合意 | 約束などの今の中身が要求どおりかを人が確かめ、認めること。動作は「合意する」（「了承」から改名した） |
| 提案中 | 今の中身に、まだ合意していない状態。一度も合意していないものと、前の合意から中身が変わったものの両方を含む |
| 合意済 | 今の中身に合意している状態 |
| ベースブランチ | 差分を出すときに比べるブランチ。ブランチごとのレビュー（RV-13）では、そのブランチが分かれた点と比べる。画面でその場で選ぶ（「比べる元」から改名した） |
| AI 案 | フラグ（注意して読む手がかり）。要求にも質疑にもなく、AI が自分で決めたもの |
| 推測 | フラグ（注意して読む手がかり）。AI が確かめずに書いた事実を含むもの |
| 差分あり | フラグ（注意して読む手がかり）。前の合意から中身が変わったもの |
| 根拠 | 調査やインタビューで分かり、判断の根拠にしたこと |
| 判断 | 決めたこと。合意、差し戻し、方針の決定 |
| 阻害要因 | 判断できない理由と、何が分かれば判断できるか |
| 差し戻し | 「このままでは合意しない」という判断 |
| 差し戻し中 | 最後の判断が差し戻しで、まだ直していない状態 |

## エージェントと CLI

| 言葉 | 意味 |
|---|---|
| 待機中 | エージェントが、レビュー・質問への回答・入力を待っている状態 |
| 中断 | エージェントの今の作業だけを止めること（コンソールで Esc を押すのに当たる） |
| 審査 | CLI の `vanda check` が行う、約束リスト・合意・エビデンス・オラクルなどの点検。証拠を見て、間違いや矛盾がなく基準を満たすかを判断する（「確かめ」から改名した） |
| エクスポート | 読み取り専用の頁を作ること |
| フラグ | 注意して読む手がかりとして、約束などに立てるもの。AI 案・推測・差分あり |
| アノテーション | 仕様・テスト・本番のコードに書く注釈。約束などの ID を指す（例: `@assurance:evidence <約束の ID>`）。quenta の規則では「印」 |
| アダプタ | vanda と、言語や道具・ストーリーの置き場所とのあいだを受け渡す部品。vanda が組込みで持つもの（組込みのアダプタ）と、プロジェクトが `.vanda/adapters/` に置くものがある |
| 組込みのアダプタ | vanda が中に持つアダプタ（アノテーションの `go`・`txtar`・`tla`・`sql`、ストーリーの置き場所の `github`）。同じ名前のアダプタを `.vanda/adapters/` に置くと、そちらが使われる |
