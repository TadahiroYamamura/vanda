# 約束リストの作り直し: 層と関係の草案

オーナーと決めたことの記録と、まだ決めていないことの一覧。約束リストと規則はまだ変えない。

## 1. 層

抽象から具体の順に 4 つ。

| 名前 | 英語の名前 | 中身 | 約束リストの書き方 |
|---|---|---|---|
| 性質層 | property level | ソフトウェアが満たすべき性質。提供すべき価値と、セキュリティなどの守るべき決まりを書く | `[[property]]`（新しい型） |
| 機能層 | feature level | 性質を実現するための機能 | `[[feature]]` |
| 仕様層 | spec level | 機能が満たすべき事前条件・事後条件・不変条件・制約・受け入れ条件 | `[[claim]]` |
| エビデンス層 | evidence level | 仕様が支持されている証拠 | `[[claim.evidence]]` |

層は型だけで表す。層を書く欄（`level`）は作らない。英語の名前は、画面や出力で層を呼ぶ時に使う。

4 つの層を横断するものが 2 つある。「層」とは呼ばない。

| 名前 | 中身 | 約束リストの書き方 |
|---|---|---|
| 用語 | ユビキタス言語の定義 | `[[term]]` |
| 前提 | 用語や約束の前提となる事実。検証されず、vanda の中では常に成り立つものとして扱う | `truth`（新しい型） |

## 2. 決めたこと

- 読む人を層で分けない。下の層だけが変わるストーリーでも、オーナーのレビューは要る
- オーナーがどの粒度まで確認するかは、チームが決める。vanda が決めるのは「開発者が細かくチェックし、オーナーが全体をチェックする」程度まで
- 層は、どの層の変更も上とのつながりの中で見せ、読む人が深さを選べるようにするために使う
- 性質層の約束は、反証できる抽象度では書かない。エビデンスを付けない
- 性質層と仕様層は、同じ `[[claim]]` として扱わず、別の型にする。性質層の型は `[[property]]`
- 十分性（上位の約束が下位の約束により抜け漏れなく具体化されていること）は、人が確認する。機械では判断できない
- 十分性の確認は、層のつなぎ目ごとに行い、下にあるものの組に結びつける。確認は 2 種類ある（「この性質は、これらの機能で具体化し切れている」と「この機能は、これらの仕様で具体化し切れている」）
- 機能が変わると、上の性質の十分性の確認が失効する。仕様が変わると、上の機能の十分性の確認が失効する。失効したものは、確認し直すことを求める
- 性質の十分性の確認内容を承認する画面では、機能の文だけを並べる。ただし、機能の仕様をその場で確認できる手段（クリックで展開する、詳細の画面へ移る、など）を必ず用意する
- 十分性は、開発者（人）が確認して確認内容を記録し、オーナーがその確認内容を承認する（エビデンスと同じ分担）。開発者（AI）が行うのは、確認の材料を作ることまで
- 十分性の確認内容として vanda に記録するのは、対象（性質か機能）、下の組のフィンガープリント、確認した人、日時。判断の根拠は vanda に書かない（GitHub の PR の本文など、ほかの場所に書く）
- 十分性の確認の記録は、承認の記録（`.vanda/agreements.toml`）に置く。開発者の確認と、オーナーの承認を、別の種類の項目にする
- 手動で失効させる操作は、承認の記録に「失効」の項目を書き足して実現する（対象、その時のフィンガープリント、人、日時）。それより前の承認は効かなくなる。承認の記録そのものは消さない（消すと履歴の改ざんになりかねず、真正性が損なわれるため）
- ガイドワードの表（`promise-reorg-guidewords.md`）は、十分性を確認する人の道具として使う
- 日本語は「層」と呼ぶ。今の用語「レイヤー」（モデル・CLI・API・画面）と混ざらないよう、TOML とコードでは layer を層の意味で使わない
- 前提は、型 `truth` として書く。オーナーの承認の対象にする（足す・変える・消すと、承認が要る）
- 前提の文が変わっても、それを assumes している約束・用語・性質の承認は失効させない。レビューの画面で、変わった前提の下に並べて見せる。オーナーは前提を承認する際に、並んだものの一部を手動で失効させられる
- supports では、エビデンスか、支持される仕様が変わると、開発者の確認内容と、それに対するオーナーの承認が失効する（制御図の 22・23 番。まだないので、作るまでは何も失効しない）
- 関係 challenges は作らない（supports の否定にすぎないため）
- 関係 part_of は作る（例: stage を分割して名前を付けつつ、stage 全体に共通する性質は 1 か所に書く）
- part_of で親に付いた仕様は、子のすべてに当てはまる。エビデンスは子ごとに要る

## 3. 関係

約束リストに、次の関係を書けるようにする。レイヤードアーキテクチャのように、許可する組み合わせを制約し、複雑になり過ぎないようにする。向きはどれも、具体から抽象へ。

| 関係 | 意味 | 許可する型の組み合わせ | 決まっているか |
|---|---|---|---|
| part_of | 同じ種類どうしの分解（一部である） | term→term、feature→feature、claim→claim。性質（`[[property]]`）と前提（`truth`）には使えない | 決めた |
| refines | 抽象的な約束を具体化する | feature→property、claim→feature | 決めた（型を分けたことに合わせて書き直した） |
| supports | 証拠が主張を支持する | evidence→claim | 決めた |
| assumes | 主張が成り立つ前提 | claim→truth、term→truth、property→truth | 決めた。相手は truth だけ。約束が用語を使うことは mentions で表す |
| mentions | インラインの参照（例: `{@id:vanda}`。特に意味はない） | 任意（主に term で使われる想定） | 決めた |

part_of で、子か親が変わった時に起きること。

| 型 | 何が変わった時 | 起きること |
|---|---|---|
| 機能・仕様 | 子を足す・消す、親を付け替える | 1 つ上の層の十分性の確認が失効する（機能なら性質の、仕様なら機能の確認） |
| 機能・仕様 | 子の文を編集する | 同じ。part_of を親へたどり、行き着いた 1 つ上の層の十分性の確認が失効する |
| 機能・仕様 | 親の文を編集する | 同じ。子の承認は失効させない |
| 用語 | 子か親の文を編集する | 編集した用語の承認だけが失効する。レビューの画面で、親と子を一緒に見せる |

## 4. まだ決めていないこと

- 1 つの機能が複数の性質に関わる時に、上にどうまとめて見せるか
- 承認の記録の置き方。承認・取り消しが 1 件ごとにコミットを積むので、コミットのログが長くなる。すぐには解けないので保留にした
  - 約束リストは git に置いたままにする（コードと同じ時点で変わることが、チェックの土台のため）。切り離しを考えるのは承認の記録だけ
  - 「選んでおいて、確定でまとめて書く」案は採らない
  - 残っている案は、同じリポジトリの別の ref に置く、git の外（承認を受け付けるサービス）に置く、の 2 つ
- 今の「承認を取り消す」は、承認の記録を消す。「記録そのものは消さない」という失効の決定と食い違っている。失効の記録を書き足す形に揃えるかは、上の置き方と一緒に決める
