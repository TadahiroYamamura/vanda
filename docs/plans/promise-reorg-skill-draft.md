# 約束リストの作り直し: スキル promise-writing の書き直しの案

`.claude/skills/promise-writing/SKILL.md` を、層と関係の草案（`promise-reorg-layers.md`）に合わせて書き直した後の全文。スキルそのものは、約束リストの新しい形を実装するコミットで書き換える。それまでは、今のスキルに従う。

今のスキルとの違いは 3 つ。

- 今の規則（`.claude/rules/promises.md`）から、書き方の決まり（正しさ、何を仕様にするか、反証の条件、機能）を移した
- 性質・前提・関係の書き方を足した
- 「約束」を「仕様」か「項目」に、「PO」を「オーナー」に書き分けた

「名前と ID」「理由」「言葉」「参照」「フラグ」「書いた後」の章は、言葉の書き分けのほかは変えていない。

下の線から後ろが、書き直した後のスキル。frontmatter の `description` は「約束リスト（.vanda/promises.toml）の項目（性質・機能・仕様・エビデンス・用語・前提）を書いたり直したりするときに使う。「仕様にして」「約束リストに書いて」「用語を足して」などの依頼で使う」にする。

# 約束リストの書き方

約束リストは、ソフトウェアについて正とする一覧。オーナーはソースコードを読まず、約束リストの文を読んで承認する。オーナーが読んで誤解しない文にする。

間違いの検出に役立たない項目は、オーナーが読む量と、保守の手間を増やすだけなので書かない。

## 項目の役割

| 種類 | 書くこと | 書かないこと |
|---|---|---|
| 性質 | ソフトウェアが満たすべき性質。提供すべき価値と、セキュリティなどの守るべき決まり | 反証できるほど具体的な条件（仕様に書く） |
| 機能 | 性質を実現するために実装するもの | 実現する性質を言えないもの、ほかの機能の部品（画面の部品、表示の細部） |
| 仕様 | 機能が満たすべき事前条件・事後条件・不変条件・制約・受け入れ条件。1 件に 1 つ | 正しさを実現する手段、関知しないこと |
| 用語 | それが何か（ものや概念の意味）。意味を決めるのに要る区別（例: 誤りとエラーの違い） | 振る舞い、作り方、決まり |
| 前提 | ソフトウェアが定義しないもの（外のサービス、人、使う道具など）についての事実で、成り立たないと性質・仕様・用語が成り立たなくなるもの | ソフトウェアが自分で守れること（仕様に書く） |

- 種類の一覧は、用語の `part_of` で表す（例: チェックの種類は、用語「チェック」の一部として並べる）
- 用語や機能の定義から振る舞いを外すときは、その振る舞いを書いた仕様があることを確かめる。なければ仕様を足す。定義から外したせいで、どこにも書かれない振る舞いを出さない

## 正しさ

性質と仕様は、次の 3 つの正しさのどれか 1 つ以上に属する。

| 正しさ | 中身 |
|---|---|
| 規範的 | 外から課された決まりに従っている（法令、セキュリティ、プロトコルの仕様、明文化された業務ルール、他社との契約、外との取り決め） |
| 機能的 | 不変条件が守られ、想定した入力に対して想定どおりの出力が出る |
| 目的的 | 使いやすい、理解しやすい、役に立つ、期待を裏切らない。人の評価が要ることが多い |

## 層のつなぎ方

- 機能は性質に、仕様は機能に、`refines` でつなぐ。層を飛ばさない（仕様を性質に直接つながない）
- 性質は、上の性質に `refines` でつないで、何段にも分けられる。機能をつなげるのは、下に性質を持たない性質だけ
- 1 つの機能が 2 つの性質を具体化する時は、両方に `refines` でつなぐ。同じ性質を 2 か所に書かない
- 機能・仕様は、層の中で 2 段にしない。2 段に分けたくなったら、上の性質として書くべきものか、テストに移すべき細部が混ざっていないかを見直す
- 前提に頼る項目は、`assumes` で前提につなぐ
- 関係の種類と、書ける組み合わせの一覧は `docs/formats.md` にある。書けない組み合わせは、チェックが誤りにする

## 性質

- 性質は、反証できる抽象度では書かない。エビデンスを付けない
- 性質の理由は、ふつうは書かない。オーナーが理由を述べた時は、その内容を書く。自分で理由に気づいた時は、書く前に質問し、オーナーが書くことを承認した時だけ書く
- 性質が満たされていることは、下の層（機能と仕様）が十分に具体化していることで示す。十分かは人が確認するので、確認する人が読んで判断できる文にする

## 機能

- 機能の抽象度を高く保つ。機能は、性質を実現するためのもので、作業の単位や画面の単位ではない
- 実現する性質を言えないものは、機能にしない

## 仕様

- 仕様にするのは、正しさのどれかに属し、反証できるものだけ。正しいかを確かめられない仕様には意味がない
- 仕様は、受け入れ基準の粒度で書く。正しさを実現する手段（並びの順、番号、件数の出し方、文言など）は仕様にせず、コードとテストに置く（例: 「一覧に通し番号を振る」ではなく「オーナーは、ストーリーで変わったすべての項目を漏れなく閲覧し、承認するかフィードバックできる」）
- 関知しないこと（どちらでもよいこと）は書かない。書くと、将来直すときの縛りになる
- 細かい場面の振る舞いは、性質から決める。承認の判定のように TLA+ のモデルがあるものは、オーナーに 1 つずつ聞かず、TLC で反例を探して決める。オーナーに聞くのは、性質どうしがぶつかるときと、性質から決まらないときだけ

## 反証の条件

- 文だけでは破れた状態が読み取れない仕様（主に目的的正しさ）には、大まかな反証の条件を書く
- エビデンスには、具体的な反証の条件（テストが確かめること、数値のしきい値、レビューで見る点）を必ず書く。テストを書く側が通しやすい条件を自分で決めないよう、仕様の文と大まかな反証の条件に答える形にする

## 前提

- 前提は検証されず、常に成り立つものとして扱われる。エビデンスを用意しにくい仕様を、前提に書き換えてはならない
- 前提を足す・変える・消すには、オーナーの承認が要る。足す前に質問する

## 名前と ID

- 機能の名前は、動詞の形にする（例: 「承認を取り消す」。「承認の取り消し」ではない）
- 機能の ID は「動詞-名詞」の形にする（例: `run-checks`、`show-claim-origin`）
- 機能の名前を、用語の名前に「する」を付けただけの形にしない（例: 「承認する」ではなく「レビューで承認する」）。文の中のふつうの動詞と同じ字になり、参照に書き換える時に、用語を指す所が機能を指してしまう。コマンドの名前を括弧で添えて字がずれるもの（「チェックする（vanda check）」）は、まぎれないのでよい
- 文の中で動詞として使う時は、用語を参照して「する」を続ける（`{@id:agreement}する`）。機能を参照するのは、その操作を名指しする時だけにする
- ID は、項目のあいだで重ならないようにする（例: チェックの agreement は、用語「承認」の `agreement` と重なるので `agreement-check` にする）

## 理由（rationale）

- そうする理由を書く。仕組みの言い換え（「〜で探すため」）は理由にならない
- オーナーが決めたことには、オーナーが述べた理由を書く。「オーナーの決定」のような、誰が決めたかの印は書かない。後から読む人に要るのは、約束リストに書かれて承認されているという事実と、理由の中身

## 言葉

- 約束リストで定義した用語を使う。定義のない語を使いたくなったら、先に用語を足す
- 用語の区別を守る。例:
  - 誤り: 人が書いたものの間違い。エラー: 処理を続けられない失敗
  - カスタムアダプタ、vanda サーバー、ソフトウェア
- 動詞の連用形を名詞にしない（「作るかの確かめ」ではなく「作るかどうかを確かめる問い」。「承認し直しにする」ではなく「承認し直すことを求める」）
- 1 文に条件を詰めない。条件が 2 つを超えたら、句点で区切る
- 消えた文書への参照（昔の仕様の番号など）を書かない

## 参照

- 名前を除く、自然言語で書く項目の欄（用語・機能の definition、仕様の statement・rationale・condition・guesses・model_check_waiver など）で、ほかの項目を指す時は、名前を文字のまま書かず、`{@id:<ID>}` と書く。画面では、用語と機能は名前に、仕様は ID に置き換えて出す
- 用語・機能の名前が、その意味でなく、ほかの語の一部やふつうの言葉として出てくる時は、参照にしない（例: `vanda check` の vanda、標準エラーのエラー）
- かぎかっこで囲んだ、画面や CLI にそのまま出す文言の中は、参照にしない。参照にすると、用語の名前を変えた時に、仕様の文言だけが変わってしまう（用語「チェック」のように用語を名指しする形は除く）
- 文字の `{@` は `{@@` と書く
- 参照の文は、置き換えた後の文として読めるように書く（参照の前後の助詞を、名前に続けて読んで不自然にしない）
- 文字のまま書いた名前をまとめて参照に書き換える時は、付属の `refs.py` を使う
  1. `python3 refs.py candidates .vanda/promises.toml` で、名前を長い順に当てた候補を出す
  2. 候補ごとに、その語がその用語・機能を指しているかを haiku に判定させる（1 回に 20 件ほど。1 回ごとに新しいエージェントにする。入力は、文・語・その用語の定義だけにする）
  3. 「いいえ」「迷った」と、まぎれやすい名前の「はい」を、親が見直して採るものを決める
  4. 外した候補があれば、`python3 refs.py candidates .vanda/promises.toml <外した候補>` で当て直し、新しく出た候補も 2・3 で決める（端が重なる名前は、長いほうに隠れて最初は候補に出ない）
  5. 書き換えの後の差分を、haiku とは別のモデル（sonnet と opus）にも見直させ、間違った参照を挙げさせる
  6. `python3 refs.py apply .vanda/promises.toml <採る候補>` で書き換え、`python3 refs.py verify <前> <後>` で、参照を名前に置き換えた文が書き換えの前と同じかを確かめる

## フラグ

- AI が書いた項目には `flags = ["ai-proposal"]` を付ける
- コードや文書から推し量って書いた所には、`guesses` に何を推し量ったかを書く

## 書いた後

- 書いた文の日本語を、別のエージェントに確かめさせる
  - 書いた本人は、言いたいことを知っているので、抜けた主語や不自然な言い回しを補って読んでしまう。そのため、文脈を持たないエージェントに読ませる
  - 確かめ役には、モデルに haiku を指定する。範囲を狭めれば haiku でも不自然な所をよく見つけるので、渡すのは差分の文だけにする（`git diff -U0 .vanda/promises.toml` で変わった文）
  - 確かめ役には、文ごとに「日本語として不自然な所があるか」と「どの箇所か、何が不自然か」だけを答えさせる
  - 確かめ役の指摘を採るかは、書いた本人が決める。確かめ役は用語の定義を知らないので、定義した用語（承認済、失効した承認 など）を言い換える案や、意味を変える案を出すことがある。採らなかった指摘は報告しない
- `vanda check` の promise-list-shape が「通った」になることを確かめてからコミットする。TOML の文字列の中の `\` は `\\` と書く
- コミットメッセージの末尾に `Story: <ストーリーの ID>` のトレーラーを書く。このトレーラーは、Co-Authored-By などのほかのトレーラーと空行をはさまず、同じ段落に書く
- 直した項目の ID と、オーナーが承認するときに見るべき所（自分で決めたこと）を報告する
- 項目を足す・変える・消すと、上の層の十分性の確認が失効する。どの性質・機能の確認が失効したかを報告する
