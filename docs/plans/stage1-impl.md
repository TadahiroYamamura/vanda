# vanda 段 1 の実装の計画（開発者向け）

この計画は、vanda の段 1 を実装する開発者のエージェントに渡す。テストの計画（`docs/plans/stage1-test.md`）は、別のテスト担当のエージェントに渡す。開発者は、テスト担当のテストを書き換えない。

前提として読むもの: `docs/spec.md`（機能の一覧と、データの形）、`docs/terms.md`（言葉）。言葉は `docs/terms.md` のものを使い、自分で名付けた言葉を、名前・コメント・コミットのメッセージに持ち込まない。

## 段 1 で作るもの

vanda の約束リストを書き、CI で審査できるようにする。GUI、ストーリーの置き場所との通信、実行の結果の取り込み、エージェントは、段 1 では作らない。

| 番号 | 機能 | 段 1 で作る範囲 |
|---|---|---|
| CM-02 | 約束リストを読む | すべて |
| CM-03 | 合意の記録を読む | 読むだけ（書くのは段 2 の GUI） |
| CM-09 | 設定のファイル | 段 1 で使う項目だけ（下の「設定」） |
| CMD-01 | 設定とつながりを確かめる | 設定と版の確かめだけ（つながりは段 2 から） |
| CMD-03 | 審査を実行する | すべて |
| CMD-10 | 審査の種類 | 下の「審査」の表のもの |
| （アダプタ） | アノテーションの読み取り | Go、シナリオ（`.txtar`）、TLA+ の 3 つを vanda の中に持つ。外部のコマンドのアダプタの受け渡しも作る |
| （アダプタ） | ガードレールの定義の取り出し | 「ファイルを読むだけ」のアダプタだけ |

## リポジトリの作り

- Go のモジュール `github.com/TadahiroYamamura/vanda`。1 つの実行ファイル `vanda`（`cmd/vanda`）
- Go の版は、quenta と同じく、その時点で nixpkgs にある安定版
- 開発の道具は nix の flake で揃える（Go、TLA+ の道具（`tlaplus`）、`git`）
- CI は GitHub Actions で、Linux と macOS の両方で `make check` を動かす
- 段 2 で React の画面を足すので、画面のファイルを置く場所（`web/`）だけを空けておく。段 1 では作らない

## 依存（PO の了承が要る）

| 依存 | 使う所 | 選んだ理由 |
|---|---|---|
| `github.com/BurntSushi/toml` | 約束リスト・合意の記録・設定の読み込み | TOML の読み込みで最も使われていて、長く安定している。項目の位置（行）を取れるので、エラーで場所を示せる |

これら以外の依存を足すときは、足す前に監督（私）に聞く。

## 作る部品

### 1. 設定（`.vanda/config.toml`）

段 1 で読む項目:

| 項目 | 中身 |
|---|---|
| `version` | 使う vanda の版。動いている vanda が古ければエラー（上げるよう知らせる）。新しければエラー（移行のコマンドを使うよう知らせる。移行のコマンドそのものは段 1 では作らない。版が 1 つしかないため） |
| ファイル | 約束リストと合意の記録の、読むファイルやパターン。既定は `.vanda/promises.toml`、`.vanda/agreements.toml` |
| レイヤー | レイヤーの一覧（ID、名前、説明） |
| アノテーション | 読むファイルのパターンと、使うアダプタ（`go`、`txtar`、`tla`、または外部のコマンド） |
| ガードレール | ガードレールの定義の取り出しのアダプタ（段 1 では「ファイルを読むだけ」） |
| ストーリー | コミットのメッセージの中の ID の書き方（段 1 では、GitHub Issues の既定 `#<数>` と、設定で書いた書き方） |

### 2. 約束リスト（`.vanda/promises.toml`）

表は `[[term]]`・`[[feature]]`・`[[claim]]`。

| 表 | 項目 |
|---|---|
| `term` | `id`、`name`、`definition`、`part_of`（省いてよい） |
| `feature` | `id`、`name`、`definition`、`core`（真偽）、`formal`（真偽。`core = true` で省けば真とみなす）、`formal_waiver`（`core = true` かつ `formal = false` のときの、形式手法を使わない理由） |
| `claim` | `id`、`subjects`（用語・機能の ID の配列）、`statement`、`rationale`、`condition`、`layers`（1 つ以上）、`flags`（`ai-proposal` だけ）、`guesses`（文の配列）、`evidence`（配列） |
| `claim.evidence` | `stage`（計画・実装・テスト・リリース・運用）、`type`（`docs/spec.md` の「エビデンスのタイプ」の 12 の値）、`layers`（1 つ以上。約束の `layers` の中から）、`detail` |

- ID は英小文字・数字をハイフンでつないだ形。用語・機能・約束の ID のどれとも重ならない
- 複数のファイルに分けられる（設定のパターン）。分けても、ID はすべてのファイルを通して重ならない

### 3. 合意の記録（`.vanda/agreements.toml`）

`[[agreement]]` の 1 件ごとに: 対象の種類（`claim`・`term`・`feature`・`file`）、鍵（約束・用語・機能なら ID、ファイルなら中身の指紋）、指紋、ファイルなら合意したときの場所、`user.name`、`user.email`、日時、ストーリーの ID。

- 今の中身の指紋に合う合意が 1 つでもあれば合意済
- 指紋は、約束リストの項目なら、読み込んだ中身から `flags` と `guesses` を除いたものを、決まった形（項目の名前の順に並べた JSON など）にしてから作る。項目の順・空白・引用符の違いでは変わらない
- ファイルの指紋は、中身そのものから作る

### 4. アノテーションの読み取り

- 読むファイルの中のコメントから `@vanda:<種類> <ID または理由>` を探す。種類は `term`・`feature`・`claim`・`internal`・`evidence`・`sensor`
- 付いているものの名前を、アダプタが読み取る
  - Go: 次の `func` の名前（テストなら `TestXxx`）
  - シナリオ（`.txtar`）: ファイルの名前。ファイルの冒頭の注釈の行に書いたものは、ファイル全体に付く
  - TLA+: 次の定義の名前（`Name ==`、`Name(...) ==`）
- 外部のコマンドのアダプタ: vanda がファイルの場所を渡し、アダプタはアノテーションごとの名前を JSON で返す。受け渡しの形は、段 1 で決めて `docs/` に書く（v1.0.0 からは変えない取り決めになる）
- 読むファイルのパターンに当たったのに、アダプタが決まっていないファイルは、審査で止める

### 5. 審査（`vanda check <審査の設定のファイル> [--base <ブランチ>]`）

審査の設定のファイル（`.vanda/checks/<名前>.toml`）に、行う審査を行う順に並べる。審査ごとに範囲（全部か、1 つのストーリーで変わったものか）を書く。範囲を「1 つのストーリー」にする審査を含むなら、`--base` は必須。どれかの審査が失敗したら、終了コードを失敗にする（「知らせるだけ」の段はない）。

段 1 で作る審査:

| 審査 | 中身 |
|---|---|
| 約束リストの形 | 読める。決まった表と項目だけがあり、必須の項目がある。ステージとタイプとレイヤーが決まった値の中にある。ID の形と重なり。`part_of` の先があり、循環しない。`subjects` の先がある。エビデンスの `layers` が約束の `layers` の中にある。約束に書いたどのレイヤーにも、それを確かめるエビデンスが 1 つ以上ある。`core = true` かつ `formal = false` なら `formal_waiver` がある |
| アノテーションのつながり | アノテーションが指す ID が約束リストにあり、種類が合う（`term` には用語、`feature` には機能、`claim`・`evidence`・`sensor` には約束）。仕様の型の宣言には `term` か `internal` がある（TLA+ では対象の決め方を、段 1 の中で監督と相談して決める） |
| 由来 | ベースブランチから分かれた点より後の、約束リストを変えたコミットに、ストーリーの ID がある |
| 合意 | 今の中身がすべて合意済（約束・用語・機能と、エビデンスの本体（シナリオ、ガードレールの定義、オラクルの定義のファイル））。フラグ（`flags`・`guesses`）が残っていない。範囲を 1 つのストーリーにしたときは、そのストーリーが前に合意したのに、ほかのストーリーの変更で今の中身に合わなくなったものも含める |
| 合意の記録の指す先 | 合意の記録が、約束リストにない約束・用語・機能を指していない |
| エビデンスが揃っている | 予定したエビデンスごとに、アノテーションの付いたもの、または `detail` に書いたファイルがある（合格しているかは段 3） |
| 読まれていないファイル | `.vanda/` にあるのに、設定のどのパターンにも当たらないファイルがない |

- 「1 つのストーリーで変わったもの」は、`--base` のブランチと今のブランチが分かれた点からの差分で決める。git は `git` のコマンドを呼んで使う
- エラーのメッセージには、どのファイルの何行目の、何がいけないか、どう直せばよいかを書く

### 6. CLI

| コマンド | 中身 |
|---|---|
| `vanda check <審査の設定のファイル> [--base <ブランチ>]` | 審査 |
| `vanda doctor` | 設定と版を確かめる（CMD-01 の段 1 の範囲） |
| `vanda version` | 版を出す |

### 7. TLA+ のモデル

vanda 自身で vanda を作る進め方へ切り替えやすくするため、段 1 で次のモデルを TLA+ で書き、TLC で検査する。CI でも検査する。

- 合意の判定: 約束の中身の変更、合意、ストーリーをまたいだ変更（ストーリー A の変更で、ストーリー B の合意が外れる）を操作とし、「今の中身の指紋に合う合意があるときだけ合意済」「B の範囲の審査は、B の外れた合意があるあいだ止まる」を性質にする

モデルは、テスト担当がクロスチェックのオラクルとして使う。モデルの形は、テスト担当と食い違わないよう、書き始める前に監督に見せる。

## 進め方

1. 部品ごとに、小さく作ってコミットする。コミットのメッセージは日本語で、`(type) subject` の形（`feat`・`fix`・`test`・`docs`・`refactor`・`chore`）
2. 作った部品ごとに、監督に報告する。報告には、作ったもの、計画から外れたこと、迷ったことを書く
3. 計画にない判断（項目の名前、エラーのメッセージの形、外部のアダプタの受け渡しの形など）は、作る前に監督に聞く
4. `panic` は使わない。エラーは値として返す
5. プッシュはしない（監督が、PO の指示を受けて行う）。リポジトリの設定（GitHub の設定、ブランチの保護）を変えない
