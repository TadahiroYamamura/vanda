# 約束リストの作り直し: 性質の木の草案

オーナーと決めた性質の木と、上の側の約束の草案（`promise-reorg-upper-claims.md`）の 21 件を、その木の下に置き直した結果。約束リストはまだ変えない。

## 1. 決め方

- 性質は、今の約束を下から束ねず、上から導く。下から束ねると、今の vanda にない性質が出てこない
- 性質に書くのは、vanda というソフトウェアが満たすこと。開発プロセス（誰が何をするか）は書かない。見分ける問いは「vanda のコードだけで、守ることも破ることもできるか」
- vanda は、正しく作るための道具ではなく、誤りを防ぐための道具。事前に想定した誤りを、なるべく早く検知する。正しさを追うと、形式手法やアシュアランスケースのような重いプロセスに行き着き、速度の目標を達成できない
- vanda が責任を持つのは、誤りを見つけることまで。直し方がすぐ分かる伝え方にするのは、vanda を使う開発者の責任
- vanda のコードだけでは守れない目的（AI による自律的な開発、安全かつ高速な開発、3 倍の速度）は、性質にせず、README に書く

## 2. 性質の木

柱は 4 つ。

| # | 性質 | 下の性質の数 |
|---|---|---|
| A | Accountability の設計: オーナーと開発者は、Accountability を体系的に設計できる。構成要素のそれぞれがどの程度実現されているかを判断でき、改善できる | 7 |
| B | 制御された失敗: 失敗を抜けなく想定し、早く検知し、致命的な状況を避けられる | 4 |
| C | vanda は、利用者の PC と秘密の情報を危険にさらさない | 0 |
| D | リスクの判断と、注意力の合理的な投下 | 3 |

### A の下（構成要素ごとに並べ、最後に説明可能性を置く）

| # | 構成要素 | 性質の文 |
|---|---|---|
| A-1 | 真正性 | 承認は、オーナーが見た中身にだけ結びつき、後から黙って変わらない |
| A-2 | 完全性・証跡性 | 承認されていない変更と、エビデンスで支持されていない仕様があれば、vanda のチェックは通らない |
| A-3 | 追跡可能性 | どの変更も、どのストーリーで、誰が何を承認したかまで辿れる |
| A-4 | 十分性 | vanda は、十分性の確認内容とその承認を記録する。下の項目が変わった時は、その確認が古くなったことを知らせる |
| A-5 | 反証可能性 | vanda は、仕様とエビデンスの反証の条件を、承認する人に見せる。反証の条件のないエビデンスを見分けられるようにする |
| A-6 | 独立性 | vanda は、実装・エビデンス・確認・承認のそれぞれを、どの主体が行ったかを記録に残す。オーナーと開発者は、その記録から、別の主体が行ったかを確かめられる |
| A-7 | （説明可能性） | vanda は、失敗の種類ごとに、4 つの備えが揃っているかを記録し、説明可能性とその内訳を見せる |

- A-7 は、A の文の後半（どの程度実現されているかを判断でき、改善できる）を受ける。説明可能性の定義は 5 章。説明可能性は B の備えの度合いで測られるが、柱は分けたままにする。B は失敗を制御する仕組みそのもの、A-7 はその備えを見えるようにするもの。失敗の種類を並べることは B-1 が受ける
- A-2 は、前提（`[[truth]]`）「チェックが通らないものは、リリースされない」を assumes する。本当に防ぎたいのは、誤ったソフトウェアがリリースされることだが、リリースを止めるのはチームの CI とリリースの進め方なので、性質の文には vanda がすることだけを書く
- A-6 の記録は、本人の申告に頼る（今は、実装担当とテスト担当のエージェントが同じ git の作者でコミットしている）。どこまで信じられるかは、機能と仕様を書く時に扱う

### B の下

| # | 性質の文 |
|---|---|
| B-1 想定 | vanda は、起こりうる誤りを抜けなく想定するための手がかりを、仕様を書く人と十分性を確認する人に渡す |
| B-2 早期検知 | 事前に想定した誤りは、何が誤りかが分かる形で、早く見つかる |
| B-3 フィードバック | オーナーは開発者（人）に、開発者（人）は開発者（AI）に、見つけた誤りをフィードバックできる。vanda は、オーナーのフィードバックを開発者（人）に届け、開発者（AI）に直接は渡さない |
| B-4 致命的な状況の回避 | リリースの前に見つけられない誤りに備えて、vanda は、リリースの後のステージのエビデンスも求め、破れた時に知らせる |

- B-3 でオーナーのフィードバックを開発者（人）に通すのは、開発者（人）の知らないうちに開発者（AI）が進めると、開発者（人）が AI の出力を詳細に確認する責任を果たせなくなるため
- B-1 と B-4 の文は、たたき台。B-4 は、ステージの今の実装を読まずに書いた

### D の下

| # | 性質の文 |
|---|---|
| D-1 | オーナーは、ソースコードを読まずに、開発者が変更した内容が誤っていないことを判断できる |
| D-2 | vanda は、注意の要る所を見分けられるようにし、読む量を判断に要る分だけに保つ |
| D-3 | vanda は、開発者（人）が確認した内容を記録し、オーナーに見せる。オーナーは、開発者（人）の確認の上に立って、全体を判断する |

- D-3 を実現する機能（開発者（人）の確認内容を記録する）は、A-2 にも refines でつなぐ

## 3. 性質にしなかったもの

### 分かったこと

- 一番下の性質 15 のうち、8 つ（A-4、A-5、A-6、A-7、B-1、B-3、B-4、D-3）に、つながる機能も仕様もない。草案は今の約束をまとめ直したものなので、これは「今の vanda にない」ことをほぼ表す。ただし、今の約束リスト 298 件を当てて確かめてはいない（ステージやフィードバックに当たる約束が、草案の 21 件に束ねられずに残っている可能性がある）
- 仕様のある 7 つは、A の前半（真正性、完全性・証跡性、追跡可能性）と D-1 に偏っている。B（制御された失敗）は、B-2 だけ
- run-checks は 3 つの性質（A-2、A-3、B-2）に、connect-story-store は 3 つの性質（A-3、C、D-1）につながる。refines を複数書ける決定が、ここで使われる

## 5. 説明可能性の定義

Accountability がどこまで実現されているかを表す指標。今ある項目がどこまで揃っているかではなく、将来起こりうる未知の失敗に、チームがどこまで準備できているかを測る。

| 言葉 | 定義 |
|---|---|
| 説明可能である | 失敗が起きた時、それが制御された状態になること |
| 制御された状態 | 次の 4 つが成り立つ状態。早く検知される（エンドユーザーに大きな損失が出る前に、チームが気づく）。被害が致命的にならない。原因まで辿れる（どの変更で入り、どの仕様とエビデンスが抜けていて、誰が何を見て承認したかが分かる）。約束リストに戻せる（同じ失敗を次は事前に検知でき、未知だった失敗が、想定した失敗に変わる） |
| 失敗の種類 | 一番下の性質とガイドワードの組み合わせ。レッドチーミングで見つかった、この組み合わせの外の失敗も足す |
| 備えがある | ある失敗の種類について、4 つの条件のそれぞれに、手段が用意されていること |
| 説明可能性 | 失敗の種類のうち、4 つの備えが揃っているものの割合。50% とは、失敗の種類の半分に、4 つの備えが揃っている状態 |

### 失敗の種類の並べ方と、確かめ方

| 方法 | 性格 | 役割 |
|---|---|---|
| 性質とガイドワードの組み合わせ | 体系的 | 失敗の種類を、抜けの少ない形で並べる。主にする方法 |
| レッドチーミング | 確率的 | 並べた種類の外にある失敗を探す |
| わざと失敗を入れる | 確かめ | 「備えがある」と付けた見立てが当たっているかを確かめる |
| 起きた失敗の記録 | 確かめ | 実際の失敗が、制御された状態になったかを確かめる |

### 見せ方

- 上に、説明可能性を 1 つの数で出す。その下に、条件ごと（検知、被害の限定、追跡、約束リストに戻す）と、性質ごとの内訳を出す
- 説明可能性の隣に、レッドチーミングの回ごとの「並べた種類の外で見つかった失敗の件数」と「試した回数」を出す。割合にはしない
- 外の失敗から妥当に言えるのは、「外の失敗が多い・減らないなら、今の想定では網羅できていない可能性が高い」まで。「外の失敗が見つからないから、よく網羅できている」「内の割合が 75% だから、75% を覆っている」とは言えない（レッドチームは失敗を偏りなく引いていない。並べた側と似た考え方をすると同じ所を見落とす。内か外かは、種類の粗さで変わる）
- 失敗の種類に、重みは付けない。致命的な所が内訳で見えるかを確かめてから、考え直す

### 分かっている弱い所

- 「備えがある」は人の判断で、読まずに「ある」と付けられる。わざと入れた失敗で確かめて補う
- 一番下の性質 15 にガイドワードを掛けると、数百の升目になる。速度の目標とぶつかるかは、試さないと分からない。重すぎる時は、ガイドワードを絞るか、わざと失敗を入れる方法を主に切り替える
- レッドチームは、実装した主体とも、失敗の種類を並べた主体とも、別である必要がある
