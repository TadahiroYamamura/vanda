# 約束リストの作り直し: 性質の草案

オーナーと決めた性質と、上の側の約束の草案（`promise-reorg-upper-claims.md`）の 21 件を、その性質の下に置き直した結果。約束リストはまだ変えない。

## 1. 決め方

- 性質は、今の約束を下から束ねず、上から導く。下から束ねると、今の vanda にない性質が出てこない
- 性質に書くのは、vanda というソフトウェアが満たすこと。開発プロセス（誰が何をするか）は書かない。見分ける問いは「vanda のコードだけで、守ることも破ることもできるか」
- vanda は、正しく作るための道具ではなく、逸脱を防ぐための道具。事前に想定した逸脱を、なるべく早く検知する。正しさを追うと、形式手法やアシュアランスケースのような重いプロセスに行き着き、速度の目標を達成できない
- vanda が責任を持つのは、逸脱を見つけることまで。直し方がすぐ分かる伝え方にするのは、vanda を使う開発者の責任
- 性質には、理由（rationale）の欄を持たせる。書くかは任意。オーナーが理由を述べた時は、その内容を書く。開発者（AI）が理由に気づいた時は、オーナーに質問し、オーナーが書くことを承認した時だけ書く。開発者（AI）が自分で考えた理由を、確かめずに書かない（「本当に必要か」という判断を、「オーナーが述べたか、承認したか」という事実に置き換えるため）
- vanda のコードだけでは守れない目的（AI による自律的な開発、安全かつ高速な開発、3 倍の速度）は、性質にせず、README に書く

## 2. 性質

柱は 4 つ。

| # | 性質 | 下の性質の数 |
|---|---|---|
| A | 答責性の設計: オーナーと開発者は、答責性を体系的に設計できる。構成要素のそれぞれがどの程度実現されているかを判断でき、改善できる | 8 |
| B | 制御された逸脱: 逸脱を抜けなく想定し、早く検知し、致命的な状況を避けられる | 4 |
| C | vanda は、利用者の PC と秘密の情報を危険にさらさない | 0 |
| D | リスクの判断と、注意力の合理的な投下 | 3 |

### A の下（構成要素ごとに並べ、最後に答責性の実現度を置く）

| # | 構成要素 | 性質の文 |
|---|---|---|
| A-1 | 真正性 | 承認は、オーナーが見た中身にだけ結びつき、後から黙って変わらない |
| A-2 | 完全性 | 承認されていない変更があれば、vanda のチェックは通らない |
| A-3 | 証跡性 | vanda は、有効なエビデンスに支持されている仕様だけを、成立しているものとして扱う。エビデンスが有効でなくなれば、その仕様を成立しているものとして扱わない |
| A-4 | 追跡可能性 | どの変更も、どのストーリーで、誰が何を承認したかまで辿れる |
| A-5 | 十分性 | vanda は、十分性の確認内容とその承認を記録する。下の項目が変わった時は、その確認が古くなったことを知らせる |
| A-6 | 反証可能性 | vanda は、仕様とエビデンスの反証の条件を、承認する人に見せる。反証の条件のないエビデンスを見分けられるようにする |
| A-7 | 独立性 | vanda は、実装・エビデンス・確認・承認のそれぞれを、どの行為者が行ったかを記録に残す。オーナーと開発者は、その記録から、別の行為者が行ったかを確かめられる |
| A-8 | （答責性の実現度） | vanda は、逸脱の種類ごとに、4 つの条件のそれぞれに対策があるかを記録し、答責性の実現度とその内訳を見せる |

- A-2 は、「守るべきものがすべて列挙されている」という元の意味の完全性を受けない。それを保証することはできない（受けるには、「オーナーは、すべての事象を考慮し、漏れなく性質を定義できる」という、成り立たない前提が要る）。A-2 は、今想定できている範囲について、vanda の機能で提供できる完全性を書いたもの。範囲の外で見つかった逸脱は、A-2 の逸脱の形として並べ、対策を付けて、想定した逸脱に変える（B-1 とレッドチーミングが、範囲を広げる側を受ける）
- A-8 は、A の文の後半（どの程度実現されているかを判断でき、改善できる）を受ける。答責性の実現度の定義は 5 章。答責性の実現度は B の対策の揃い方で測られるが、柱は分けたままにする。B は逸脱を制御する仕組みそのもの、A-8 はその対策を見えるようにするもの。逸脱の種類を並べることは B-1 が受ける
- 証跡性とは、エビデンスが残っていることではなく、エビデンスが有効である間は、それが支持する仕様（の一部または全部）が成立していると保証されること。エビデンスが有効であるとは、エビデンスが通っていて、開発者（人）が確認し、オーナーが承認し、その後に失効していないこと。この 4 つの条件は、性質の文ではなく仕様に書く
- テストが通ることだけでは、仕様の成立は決まらない。「このエビデンスは、この仕様を確かに支持している」と開発者（人）が確認し、オーナーが承認することで、保証になる。そのため A-3 は、D-3 と A-6 に支えられる
- A-2 と A-3 は、前提（`[[truth]]`）「チェックが通らないものは、リリースされない」を assumes する。本当に防ぎたいのは、誤ったソフトウェアがリリースされることだが、リリースを止めるのはチームの CI とリリースの進め方なので、性質の文には vanda がすることだけを書く
- 行為者とは、実装、エビデンスの作成、確認、承認を行う、1 人の人または 1 つのエージェント。役割（実装担当、テスト担当）ではなく、個々の存在を指す。独立性が見たいのは、1 つの行為者が 2 つの役割を兼ねていないか。約束リストの用語に足すのは、形の実装の時
- A-7 の記録は、本人の申告に頼る（今は、実装担当とテスト担当のエージェントが同じ git の作者でコミットしている）。どこまで信じられるかは、機能と仕様を書く時に扱う

### B の下

| # | 性質の文 |
|---|---|
| B-1 想定 | vanda は、起こりうる逸脱を抜けなく想定するための手がかりを、仕様を書く人と十分性を確認する人に渡す |
| B-2 早期検知 | 事前に想定した逸脱は、どの性質からどう外れたかが分かる形で、早く見つかる |
| B-3 フィードバック | オーナーは開発者（人）に、開発者（人）は開発者（AI）に、見つけた逸脱と、承認しない理由をフィードバックできる。開発者（AI）は開発者（人）に、開発者（人）はオーナーに、約束リストの不備をフィードバックできる。vanda は、どちらの向きでも、開発者（人）を飛ばして届けない |
| B-4 致命的な状況の回避 | リリースの前に見つけられない逸脱に備えて、vanda は、リリースの後のステージのエビデンスも求め、破れた時に知らせる |

- B-3 の「オーナー ↔ 開発者（人） ↔ 開発者（AI）」の順は、必ず守る。理由は 2 つ。開発者（人）の知らないうちに開発者（AI）が進めると、開発者（人）が AI の出力を詳細に確認する責任を果たせなくなる。人の注意力は有限なので、オーナーの判断力を浪費しないよう、開発者（人）がまず受ける
- B-3 は、両向きを 1 つの性質にした。上向き（約束リストの不備を伝える）は、制御された状態の 4 つ目の条件（約束リストに戻せる）を支える。向きごとに分ける必要が出たら、考え直す
- B-1 と B-4 の文は、たたき台。B-4 は、ステージの今の実装を読まずに書いた

### 分かったこと

## 5. 答責性と、その実現度の定義

答責性がどこまで実現されているかを表す指標（答責性の実現度）。今ある項目がどこまで揃っているかではなく、将来起こりうる未知の逸脱に、チームがどこまで準備できているかを測る。

| 言葉 | 定義 |
|---|---|
| 逸脱 | ソフトウェアが、本来満たすべき性質を満たさなくなること。英語は deviation。用語「誤り」（vanda を設定する時に人が犯す間違い）と「エラー」（プログラムが出力するもの）は、どちらも開発者が受け取って直すもので、逸脱とは区別する。「失敗」は、指す範囲が広く、チェックやテストが通らないことにも使うので、この意味では使わない |
| 答責性| ソフトウェアが逸脱によって損失を出した時、チームがそれに対して責任を取れること。何が起き、事前にどんな対策を取っていて、どう最悪の事態を避けて収束させたかを、説明できること（例: チームの責任者が「X という事象が起きた。事前に Y という対策を取っていたので、最悪の事態を避け、収束させた」と説明できる）。英語の accountability に当たる。説明と責任の両方を表すふだんの日本語がなく、字から意味が取れるこの言葉にした |
| 答責性がある | 逸脱が起きた時、それが制御された状態になること |
| 制御された状態 | 次の 4 つが成り立つ状態。早く検知される（エンドユーザーに大きな損失が出る前に、チームが気づく）。被害が致命的にならない。原因まで辿れる（どの変更で入り、どの仕様とエビデンスが抜けていて、誰が何を見て承認したかが分かる）。約束リストに戻せる（同じ逸脱を次は事前に検知でき、未知だった逸脱が、想定した逸脱に変わる） |
| 逸脱の種類 | 一番下の性質、ガイドワード、逸脱の形の組。1 つの性質とガイドワードの組み合わせに、逸脱の形は複数出る（試しでは 2〜5 個）。レッドチーミングで見つかった、この組の外の逸脱も足す |
| 対策 | 逸脱が起きた時に、それを制御された状態にするために、事前に用意しておく手段。答責性の例で、責任者が「事前に Y という対策を取っていた」と説明する、その Y に当たる |
| 対策が揃っている | ある逸脱の種類について、4 つの条件のそれぞれに、対策があること。「早く検知される」と「被害が致命的にならない」は、逸脱の種類ごとに見る。「原因まで辿れる」と「約束リストに戻せる」は、性質ごとに 1 回見て、その性質の逸脱の種類すべてに同じ答えを当てる。逸脱の形によって答えが変わる性質では、その性質だけ、逸脱の種類ごとに見る |
| レッドチーム | 並べた逸脱の種類の外にある逸脱を探す行為者。実装した行為者とも、逸脱の種類を並べた行為者とも別。セキュリティに限らず、どの性質からの逸脱も探す |
| レッドチーミング | レッドチームが、逸脱を探す活動 |
| 答責性の実現度 | 逸脱の種類のうち、対策が揃っているものの割合。50% とは、逸脱の種類の半分で、対策が揃っている状態。数えるのは、機能のある性質の逸脱の種類だけ。機能がまだない性質は、分母に入れず、その数を別に見せる |

### 逸脱の種類の並べ方と、確かめ方

| 方法 | 性格 | 役割 |
|---|---|---|
| 性質とガイドワードの組み合わせ | 体系的 | 逸脱の種類を、抜けの少ない形で並べる。主にする方法 |
| レッドチーミング | 確率的 | 並べた種類の外にある逸脱を探す |
| わざと逸脱を起こす | 確かめ | 「対策がある」と付けた見立てが当たっているかを確かめる |
| 起きた逸脱の記録 | 確かめ | 実際の逸脱が、制御された状態になったかを確かめる |

### 見せ方

- 上に、答責性の実現度を 1 つの数で出す。その下に、条件ごと（検知、被害の限定、追跡、約束リストに戻す）と、性質ごとの内訳を出す
- 答責性の実現度の隣に、機能がまだない性質の数を、同じ大きさで出す。値だけを見ると、機能のない性質の分だけ、実際より良く見えるため
- 答責性の実現度の隣に、レッドチーミングの回ごとの「並べた種類の外で見つかった逸脱の件数」と「試した回数」を出す。割合にはしない
- 外の逸脱から妥当に言えるのは、「外の逸脱が多い・減らないなら、今の想定では網羅できていない可能性が高い」まで。「外の逸脱が見つからないから、よく網羅できている」「内の割合が 75% だから、75% を覆っている」とは言えない（レッドチームは逸脱を偏りなく引いていない。並べた側と似た考え方をすると同じ所を見落とす。内か外かは、種類の粗さで変わる）
- 逸脱の種類に、重みは付けない。致命的な所が内訳で見えるかを確かめてから、考え直す

### 分かっている弱い所

- 「対策がある」は人の判断で、読まずに「ある」と付けられる。わざと起こした逸脱で確かめて補う
- 一番下の性質 16 にガイドワードを掛けると、数百の升目になる。速度の目標とぶつかるかは、試さないと分からない。重すぎる時は、ガイドワードを絞るか、わざと逸脱を起こす方法を主に切り替える
- レッドチームは、実装した行為者とも、逸脱の種類を並べた行為者とも、別である必要がある
- 逸脱の形を単位に数えるので、書いた量で値が変わる。形を細かく分ければ分母が増え、対策のある形を多く書けば値が上がる。性質とガイドワードの組み合わせを単位にすると、対策のある形が数に現れない（A-2 では 6 つの組み合わせのすべてに対策のない形があり、値が 0 になる）ので、こちらを採った
