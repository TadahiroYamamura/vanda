# 約束リストの作り直し: 性質の木の草案

オーナーと決めた性質の木と、上の側の約束の草案（`promise-reorg-upper-claims.md`）の 21 件を、その木の下に置き直した結果。約束リストはまだ変えない。

## 1. 決め方

- 性質は、今の約束を下から束ねず、上から導く。下から束ねると、今の vanda にない性質が出てこない
- 性質に書くのは、vanda というソフトウェアが満たすこと。開発プロセス（誰が何をするか）は書かない。見分ける問いは「vanda のコードだけで、守ることも破ることもできるか」
- vanda は、正しく作るための道具ではなく、誤りを防ぐための道具。事前に想定した誤りを、なるべく早く検知する。正しさを追うと、形式手法やアシュアランスケースのような重いプロセスに行き着き、速度の目標を達成できない
- vanda が責任を持つのは、誤りを見つけることまで。直し方がすぐ分かる伝え方にするのは、vanda を使う開発者の責任
- 性質には、理由（rationale）の欄を持たせる。書くかは任意。オーナーが理由を述べた時は、その内容を書く。開発者（AI）が理由に気づいた時は、オーナーに質問し、オーナーが書くことを承認した時だけ書く。開発者（AI）が自分で考えた理由を、確かめずに書かない（「本当に必要か」という判断を、「オーナーが述べたか、承認したか」という事実に置き換えるため）
- vanda のコードだけでは守れない目的（AI による自律的な開発、安全かつ高速な開発、3 倍の速度）は、性質にせず、README に書く

## 2. 性質の木

柱は 4 つ。

| # | 性質 | 下の性質の数 |
|---|---|---|
| A | Accountability の設計: オーナーと開発者は、Accountability を体系的に設計できる。構成要素のそれぞれがどの程度実現されているかを判断でき、改善できる | 8 |
| B | 制御された逸脱: 逸脱を抜けなく想定し、早く検知し、致命的な状況を避けられる | 4 |
| C | vanda は、利用者の PC と秘密の情報を危険にさらさない | 0 |
| D | リスクの判断と、注意力の合理的な投下 | 3 |

### A の下（構成要素ごとに並べ、最後に説明可能性を置く）

| # | 構成要素 | 性質の文 |
|---|---|---|
| A-1 | 真正性 | 承認は、オーナーが見た中身にだけ結びつき、後から黙って変わらない |
| A-2 | 完全性 | 承認されていない変更があれば、vanda のチェックは通らない |
| A-3 | 証跡性 | vanda は、有効なエビデンスに支持されている仕様だけを、成立しているものとして扱う。エビデンスが有効でなくなれば、その仕様を成立しているものとして扱わない |
| A-4 | 追跡可能性 | どの変更も、どのストーリーで、誰が何を承認したかまで辿れる |
| A-5 | 十分性 | vanda は、十分性の確認内容とその承認を記録する。下の項目が変わった時は、その確認が古くなったことを知らせる |
| A-6 | 反証可能性 | vanda は、仕様とエビデンスの反証の条件を、承認する人に見せる。反証の条件のないエビデンスを見分けられるようにする |
| A-7 | 独立性 | vanda は、実装・エビデンス・確認・承認のそれぞれを、どの行為者が行ったかを記録に残す。オーナーと開発者は、その記録から、別の行為者が行ったかを確かめられる |
| A-8 | （説明可能性） | vanda は、逸脱の種類ごとに、4 つの備えが揃っているかを記録し、説明可能性とその内訳を見せる |

- A-8 は、A の文の後半（どの程度実現されているかを判断でき、改善できる）を受ける。説明可能性の定義は 5 章。説明可能性は B の備えの度合いで測られるが、柱は分けたままにする。B は逸脱を制御する仕組みそのもの、A-8 はその備えを見えるようにするもの。逸脱の種類を並べることは B-1 が受ける
- 証跡性とは、エビデンスが残っていることではなく、エビデンスが有効である間は、それが支持する仕様（の一部または全部）が成立していると保証されること。エビデンスが有効であるとは、エビデンスが通っていて、開発者（人）が確認し、オーナーが承認し、その後に失効していないこと。この 4 つの条件は、性質の文ではなく仕様に書く
- テストが通ることだけでは、仕様の成立は決まらない。「このエビデンスは、この仕様を確かに支持している」と開発者（人）が確認し、オーナーが承認することで、保証になる。そのため A-3 は、D-3 と A-6 に支えられる
- A-2 と A-3 は、前提（`[[truth]]`）「チェックが通らないものは、リリースされない」を assumes する。本当に防ぎたいのは、誤ったソフトウェアがリリースされることだが、リリースを止めるのはチームの CI とリリースの進め方なので、性質の文には vanda がすることだけを書く
- 行為者とは、実装、エビデンスの作成、確認、承認を行う、1 人の人または 1 つのエージェント。役割（実装担当、テスト担当）ではなく、個々の存在を指す。独立性が見たいのは、1 つの行為者が 2 つの役割を兼ねていないか。約束リストの用語に足すのは、形の実装の時
- A-7 の記録は、本人の申告に頼る（今は、実装担当とテスト担当のエージェントが同じ git の作者でコミットしている）。どこまで信じられるかは、機能と仕様を書く時に扱う

### B の下

| # | 性質の文 |
|---|---|
| B-1 想定 | vanda は、起こりうる誤りを抜けなく想定するための手がかりを、仕様を書く人と十分性を確認する人に渡す |
| B-2 早期検知 | 事前に想定した誤りは、何が誤りかが分かる形で、早く見つかる |
| B-3 フィードバック | オーナーは開発者（人）に、開発者（人）は開発者（AI）に、見つけた誤りをフィードバックできる。vanda は、オーナーのフィードバックを開発者（人）に届け、開発者（AI）に直接は渡さない |
| B-4 致命的な状況の回避 | リリースの前に見つけられない誤りに備えて、vanda は、リリースの後のステージのエビデンスも求め、破れた時に知らせる |

- B-3 でオーナーのフィードバックを開発者（人）に通すのは、開発者（人）の知らないうちに開発者（AI）が進めると、開発者（人）が AI の出力を詳細に確認する責任を果たせなくなるため
- B-1 と B-4 の文は、たたき台。B-4 は、ステージの今の実装を読まずに書いた

### D の下

| # | 性質の文 |
|---|---|
| D-1 | オーナーは、ソースコードを読まずに、開発者が変更した内容が誤っていないことを判断できる |
| D-2 | vanda は、注意の要る所を見分けられるようにし、読む量を判断に要る分だけに保つ |
| D-3 | vanda は、開発者（人）が確認した内容を記録し、オーナーに見せる。オーナーは、開発者（人）の確認の上に立って、全体を判断する |

- D-3 を実現する機能（開発者（人）の確認内容を記録する）は、A-3 にも refines でつなぐ

### 分かったこと

- 一番下の性質 16 のうち、8 つ（A-5、A-6、A-7、A-8、B-1、B-3、B-4、D-3）に、つながる機能も仕様もない。草案は今の約束をまとめ直したものなので、これは「今の vanda にない」ことをほぼ表す。ただし、今の約束リスト 298 件を当てて確かめてはいない（ステージやフィードバックに当たる約束が、草案の 21 件に束ねられずに残っている可能性がある）
- A-3 の仕様 3 件は、エビデンスが「ある」ことまでしか述べていない。エビデンスが通っていること、開発者（人）の確認、オーナーの承認、失効は、どの仕様にもない（通っていることは、実装を確かめていない）
- 仕様のある 8 つは、A の前半（真正性、完全性・証跡性、追跡可能性）と D-1 に偏っている。B（制御された逸脱）は、B-2 だけ
- run-checks は 4 つの性質（A-2、A-3、A-4、B-2）に、connect-story-store は 3 つの性質（A-4、C、D-1）につながる。refines を複数書ける決定が、ここで使われる

## 5. 説明可能性の定義

Accountability がどこまで実現されているかを表す指標。今ある項目がどこまで揃っているかではなく、将来起こりうる未知の逸脱に、チームがどこまで準備できているかを測る。

| 言葉 | 定義 |
|---|---|
| 逸脱 | ソフトウェアが、本来満たすべき性質を満たさなくなること。用語「誤り」（vanda を設定する時に人が犯す間違い）と「エラー」（プログラムが出力するもの）は、どちらも開発者が受け取って直すもので、逸脱とは区別する。「失敗」は、指す範囲が広く、チェックやテストが通らないことにも使うので、この意味では使わない |
| 説明可能である | 逸脱が起きた時、それが制御された状態になること |
| 制御された状態 | 次の 4 つが成り立つ状態。早く検知される（エンドユーザーに大きな損失が出る前に、チームが気づく）。被害が致命的にならない。原因まで辿れる（どの変更で入り、どの仕様とエビデンスが抜けていて、誰が何を見て承認したかが分かる）。約束リストに戻せる（同じ逸脱を次は事前に検知でき、未知だった逸脱が、想定した逸脱に変わる） |
| 逸脱の種類 | 一番下の性質とガイドワードの組み合わせ。レッドチーミングで見つかった、この組み合わせの外の逸脱も足す |
| 備えがある | ある逸脱の種類について、4 つの条件のそれぞれに、手段が用意されていること |
| 説明可能性 | 逸脱の種類のうち、4 つの備えが揃っているものの割合。50% とは、逸脱の種類の半分に、4 つの備えが揃っている状態 |

### 逸脱の種類の並べ方と、確かめ方

| 方法 | 性格 | 役割 |
|---|---|---|
| 性質とガイドワードの組み合わせ | 体系的 | 逸脱の種類を、抜けの少ない形で並べる。主にする方法 |
| レッドチーミング | 確率的 | 並べた種類の外にある逸脱を探す |
| わざと逸脱を起こす | 確かめ | 「備えがある」と付けた見立てが当たっているかを確かめる |
| 起きた逸脱の記録 | 確かめ | 実際の逸脱が、制御された状態になったかを確かめる |

### 見せ方

- 上に、説明可能性を 1 つの数で出す。その下に、条件ごと（検知、被害の限定、追跡、約束リストに戻す）と、性質ごとの内訳を出す
- 説明可能性の隣に、レッドチーミングの回ごとの「並べた種類の外で見つかった逸脱の件数」と「試した回数」を出す。割合にはしない
- 外の逸脱から妥当に言えるのは、「外の逸脱が多い・減らないなら、今の想定では網羅できていない可能性が高い」まで。「外の逸脱が見つからないから、よく網羅できている」「内の割合が 75% だから、75% を覆っている」とは言えない（レッドチームは逸脱を偏りなく引いていない。並べた側と似た考え方をすると同じ所を見落とす。内か外かは、種類の粗さで変わる）
- 逸脱の種類に、重みは付けない。致命的な所が内訳で見えるかを確かめてから、考え直す

### 分かっている弱い所

- 「備えがある」は人の判断で、読まずに「ある」と付けられる。わざと起こした逸脱で確かめて補う
- 一番下の性質 16 にガイドワードを掛けると、数百の升目になる。速度の目標とぶつかるかは、試さないと分からない。重すぎる時は、ガイドワードを絞るか、わざと逸脱を起こす方法を主に切り替える
- レッドチームは、実装した行為者とも、逸脱の種類を並べた行為者とも、別である必要がある

- 「レッドチーム」「レッドチーミング」を、そのまま使うか
