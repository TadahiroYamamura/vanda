# 約束リストの新しい形の実装の計画（実装担当向け）

約束リストを、4 つの層（性質・機能・仕様・エビデンス）と、横断する 2 つ（用語・前提）を持つ形に作り直す。この計画は、全体の段と、最初の段（段 1）の作り方を書く。段 1 は、実装担当のエージェントに渡す。テストの計画（`docs/plans/promise-reorg-shape-test.md`）は、テスト担当のエージェントに渡す。

前提として読むもの: `CLAUDE.md`、`docs/plans/promise-reorg-layers.md`（決めたことと理由）、`docs/plans/promise-reorg-properties.md`（性質の草案）、`docs/spec.md` の「約束リストの層と関係」、`docs/formats.md` の「約束リスト」「承認の記録」「アノテーション」、`docs/pitfalls.jsonl`。

この計画は、オーナーの承認を得るまで、実装担当に渡さない。

## 1. 全体の段

| 段 | 作るもの | 受ける性質 |
|---|---|---|
| 1 | 型（性質・前提・仕様）と関係（refines・assumes）を読む。書けない組み合わせを、約束リストの形のチェックで誤りにする。性質と前提を、承認の対象にする。vanda 自身の約束リストを、性質から書き直す（性質、機能、仕様）。言葉を書き分ける。要らない機能を消す | 層の土台 |
| 2 | 十分性の確認を、開発者（人）が記録し、オーナーが承認する。下の組が変わると失効する | A-5 |
| 3 | レビューの画面で、下の層の変更を、上の層とのつながりの中で見せる。変わった前提の下に、それを assumes する項目を並べる | D-1 |

- 段 2 より後の計画は、段 1 が終わってから書く。段 1 で形が動くと、後の段の作り方が変わるため
- 保留の 3 件（承認の記録の置き方、取り消しを失効の記録に揃えるか、複数の性質につながる機能の見せ方）は、段 1 では要らない。段 2 と段 3 の計画を書く時に質問する
- 初めの案では、今の機能 34 件と仕様 298 件をそのまま移し、書き直しを段 4 に置いていた。今ある機能に性質を当てはめると、性質に関わるだけの部品が、性質を実現する機能としてつながると分かったので、書き直しを段 1 に入れた

## 2. 段 1 で作るもの

### 2.1 約束リストの形

| 型 | 項目 | 変わる所 |
|---|---|---|
| `[[property]]`（新しい） | `id`（必須）、`statement`（必須）、`rationale`、`refines`（上の性質の ID の配列）、`assumes`（前提の ID の配列） | 新しい型。エビデンスは書けない |
| `[[truth]]`（新しい） | `id`（必須）、`statement`（必須） | 新しい型 |
| `[[feature]]` | 今の項目に、`refines`（性質の ID の配列。必須で、空にできない）を足す | 足す |
| `[[spec]]`（`[[claim]]` を改名） | 今の項目から `subjects` を消し、`refines`（機能の ID の配列。必須で、空にできない）と `assumes` を足す。エビデンスは `[[spec.evidence]]` | 改名と入れ替え |
| `[[term]]` | 今の項目に、`assumes` を足す。`part_of` は変えない | 足す |

- `[[claim]]` と `subjects` は、決まっていない表・項目として、今の決まりのとおり誤りになる。古い形を読み替える処理や、移し方を案内する特別な誤りは作らない（v1.0.0 より前は、後方互換を持たない）
- `subjects` に書いていた用語の ID は、どこにも移さない。項目が用語を使うことは、文の中の参照（`{@id:<ID>}`）で表す（関係 mentions）。mentions のための項目は作らない
- 層を書く欄（`level`）は作らない。TOML とコードで、layer を層の意味で使わない（今の `layers` は、レイヤー（モデル・CLI・API・画面）の意味のまま残す）

### 2.2 関係の決まり（約束リストの形のチェックで誤りにする）

| 決まり | 誤りにする場合 |
|---|---|
| 指す先がある | `refines`・`assumes` の ID の項目がない |
| refines の組み合わせ | 性質の `refines` が性質でない。機能の `refines` が性質でない。仕様の `refines` が機能でない |
| 機能をつなげる性質 | 機能が `refines` する性質に、それを `refines` する性質がある（下に性質を持つ性質には、機能をつなげない） |
| assumes の相手 | `assumes` の ID が前提でない |
| 循環しない | 性質の `refines` をたどると、自分に戻る |
| 重ならない | 同じ配列の中に、同じ ID が 2 度ある |
| ID が重ならない | 性質・前提の ID が、用語・機能・仕様・ほかの性質・前提の ID と同じ（今の決まりを、新しい型に広げる） |

- 一番上の性質（`refines` を書かない性質）は、いくつあってもよい
- 下に何もつながっていない性質（性質も機能も `refines` していない）は、段 1 では誤りにしない。段 2 で、十分性の確認がないものとして見せる
- 誤りの文は、今の決まり（です・ます調の 1 行で「<何がどうなっているか>。<どうすればよいか>。」）に従う

### 2.3 参照

- `{@id:<ID>}` で、性質と前提も指せるようにする。画面では、性質と前提は ID に置き換えて出す（仕様と同じ）
- フィンガープリントは、今と同じく、参照を置き換える前の、書いたままの文から作る

### 2.4 フィンガープリントと承認

| もの | 決まり |
|---|---|
| 性質・前提のフィンガープリント | 用語・機能と同じ作り方（項目の表を、決まった形の JSON にしたもの） |
| 仕様のフィンガープリント | 今の約束と同じ（`flags` と `guesses` を除く）。`refines` と `assumes` は含む |
| 承認の対象 | 今の対象に、性質と前提を足す |
| 承認の記録の `kind` | `claim` を `spec` に改名し、`property` と `truth` を足す |
| 消したことへの承認、失効した承認、ID を変えた時の扱い | 性質と前提にも、今の決まりをそのまま当てる |
| フラグ | `flags` と `guesses` は、仕様だけが持つ（今と同じ）。性質と前提には足さない |

- 関係の先（`refines` で指された性質など）が変わっても、指している側の承認は失効させない。段 1 で失効が起きるのは、その項目の表が変わった時だけ
- 承認の判定の TLA+ のモデル（`spec/`）は、判定の決まりが変わらないので、段 1 では変えない。定義の名前に約束を指す言葉があれば、言葉の書き分けだけを行う

### 2.5 アノテーション

| もの | 決まり |
|---|---|
| `@vanda:claim <ID>` | `@vanda:spec <ID>` に改名する。`@vanda:claim` は、決まっていない種類として誤りになる |
| `@vanda:evidence`・`@vanda:sensor` | 変えない（仕様を指す） |
| 性質・前提を指すアノテーション | 作らない。性質にはエビデンスを付けず、前提は検証しないため |

リポジトリの中の `@vanda:claim`（75 か所）は、改名し、指す先を 2.8 の対応の表に従って付け直す。

### 2.6 チェック・画面・API

段 1 では、新しい型を読めて、承認できる所までを作る。層のつながりを見せる画面は、段 3 で作る。

| 所 | 段 1 で行うこと |
|---|---|
| チェック | 2.2 の決まりを promise-list-shape に足す。agreement・agreement-targets に、性質と前提を足す。evidence-present は、仕様だけを見る（今と同じ） |
| 変わったものの一覧 | 性質と前提を、種類の 1 つとして一覧に出す。承認と取り消しができる |
| 詳細の画面 | 性質と前提の詳細（文、理由、`refines` と `assumes` の先、由来、承認の履歴）を出す。機能と仕様の詳細に、`refines` の先を出す |
| API | 型の名前（`claim`）を持つパスと項目を、`spec` に改名する。性質と前提の項目を足す |
| 出力と画面の文言 | 2.7 の言葉の書き分けに従う |

### 2.7 言葉

| 今 | 後 |
|---|---|
| 約束（`[[claim]]` の項目を指す時） | 仕様 |
| 約束（用語・機能なども含めて指す時） | 項目 |
| 約束リスト | 変えない |
| PO | オーナー |
| 監督 | 使わない（文に応じて、オーナーか開発者（人）にする） |

- 書き分ける所: チェックの誤りの文、画面、コードのコメントと名前、`docs/formats.md`、`docs/spec.md`、`CLAUDE.md`
- `.claude/rules/promises.md` を `docs/plans/promise-reorg-rules-draft.md` の中身に、スキル promise-writing を `docs/plans/promise-reorg-skill-draft.md` の中身に、同じ変更の中で書き換える
- 関係の種類と、書ける組み合わせの表を、`docs/formats.md` に書く
- 規則の草案に、機能にするものの基準（それなしでは目的を達成できないものだけを機能にする。部品は機能にしない。約束リストは小さく始め、要ると判断した時に足す）を足してから、書き換える

### 2.8 vanda 自身の約束リストを、性質から書き直す

今の機能と仕様を移さず、性質の側から「これがないと、その性質が成り立たない」機能を書き、機能ごとに、受け入れ基準の粒の仕様を書く。機能として管理するのは、それなしでは目的を達成できないものだけ。約束リストは小さく始め、要ると判断した時に足す。

| 書くもの | 行うこと |
|---|---|
| 性質 | `promise-reorg-properties.md` の 2 章の性質（柱 5 つ、その下 18）を書く |
| 前提 | 3 つを書く。「チェックが通らないものは、リリースされない」「リポジトリで管理されているプログラムに、悪意のあるコードは混ざっていない」「利用者の端末で、悪意のあるプログラムは動いておらず、悪意のある人は端末を操作していない」 |
| 機能 | `promise-reorg-properties.md` の「機能を、性質から書き直した結果」の 18 件を書く。今の機能 34 件は消す |
| 仕様 | `promise-reorg-properties.md` の「仕様を、機能から書き直した結果」の 24 件を書く。今の仕様 298 件は消す。細部は、テストで守る |
| 用語と機能のページ | 機能のページの「それを対象に持つ仕様の一覧」を、「その機能を refines する仕様の一覧」に置き換える。用語のページからは、一覧を外す（`subjects` がなくなるため） |
| 関係の決まり | 2.2〜2.5 の決まりは、仕様にしない。B-2 の仕様（誤りを、黙って見逃さずに知らせる）の細部として、テストで守る |
| コア機能の決まり | 機能の `core`・`formal`・`formal_waiver` と、仕様の `model_check_waiver` は、今の形のまま残す（D-2 を実現する機能） |
| 用語 | 「約束」を消し、「仕様」「項目」「性質」「前提」「層」「十分性」を足す。新しい仕様と機能が使わなくなった用語は消す。「答責性」「逸脱」などの、まだ機能のない性質の言葉は、その機能を作る段で足す |
| 対応の表 | 今の仕様 298 件のそれぞれが、新しい 24 件のどれの細部に当たるかの表を作る（この計画を書いたエージェントが作り、オーナーが見る）。段 1 の最初の部品 |
| アノテーション | 消える仕様を指す `@vanda:evidence`（795 か所）・`@vanda:sensor`（45 か所）・`@vanda:claim`（75 か所）を、対応の表に従って、新しい仕様に付け直す。どの仕様にも当たらないテスト（doctor など）は、2.9 で消すコードと一緒に消す |
| 承認の記録 | 今ある記録（137 件）をすべて消し、`.vanda/agreements.toml` を空から作り直す。承認は、書き直した後にやり直す |

- 承認の記録を消すのは、約束リストを丸ごと書き直すため。今ある記録は `main` にはなく、このブランチの git の履歴に残る
- 機能のまだない 9 つの性質（A-5、A-6、A-7、A-8、B-1、B-3、B-4、D-3、E-2）は、下に何もつながらないまま書く
- 今の機能のうち、部品に当たるもの（設定をファイルに持つ、約束リストを読む、チェックを列挙する、用語と機能の詳細を示す、など）は、機能でなくす。コードは残す

### 2.9 要らない機能を消す

| 消すもの | 行うこと |
|---|---|
| vanda doctor | コマンド、そのテスト、それだけを指す仕様を消す。誤りの文の中の「vanda doctor で誤りを確かめて」という案内を直す。`docs/formats.md` と README の説明を消す |
| vanda version | コマンドと、そのテストを消す。設定のバージョンと比べる処理は残す |

- doctor を消す前に、画面でストーリーを読めなかった時に、原因（トークンがない、リポジトリの名前が違う、など）が分かる形で出るかを確かめる。出ない時は、消す前に報告する
- ほかの機能が、消すものに頼っていると分かった時は、消さずに報告する

## 3. 段 1 で作らないもの

- 十分性の確認の記録・承認・失効（段 2）
- 手動で失効させる操作と、失効の記録（保留の件と一緒に決める）
- 前提が変わった時に、それを assumes する項目を並べて見せる画面（段 3）
- 性質ごとにたどる画面、下の層の変更を上の層の中で見せる画面（段 3）
- 開発者（人）の確認の記録、行為者の記録、テストの結果の取り込み、フィードバックの経路（`promise-reorg-properties.md` の 6 章の順で、別の計画にする）

## 4. 進め方

- 部品の順は、対応の表（2.8）、約束リストを読む所（2.1〜2.3）、フィンガープリントと承認（2.4）、アノテーション（2.5）、チェック・API・画面（2.6）、言葉（2.7）、要らない機能を消す（2.9）、約束リストを書き直す（2.8）
- 部品ごとに報告する。計画にない判断は、作る前に質問する
- 実装担当は、テストのファイルを書き換えない。型の改名で通らなくなったテストは、テスト担当に渡す
- 段 1 の間、`vanda check` は、約束リストを書き直し終えるまで通らない。部品ごとの確かめは、テストと、テスト用の小さな約束リストで行う

## 5. 決めたこと

|---|---|---|
| 1 | 性質と前提に、名前（`name`）を持たせるか | 持たせない。一覧と参照では ID を出す（仕様と同じ） |
| 2 | 仕様が、複数の機能を `refines` してよいか | よい |
| 3 | アノテーションの `@vanda:claim` を、`@vanda:spec` に改名するか | 改名する |
| 4 | 今ある承認の記録をどうするか | すべて消して、作り直す。`kind` は `claim` を `spec` に改名する |
| 5 | 段 1 で、機能の `refines` を必須にするか | 必須にする |
| 6 | 言葉の書き分けと、規則・スキルの書き換えを、段 1 に入れるか | 入れる。型の改名と同じ変更にしないと、文言と型がずれる |
| 7 | 今の機能 34 件を、どう扱うか | 移さない。性質から書き直す（18 件）。なくても目的を達成できる機能は、約束リストに書かず、コードからも消す |

| 9 | 今の仕様を指すアノテーションを、どう扱うか | 対応の表を作り、すべて新しい仕様に付け直す。1 つの仕様に多くのテストが付き、どれが反証の条件に答えているかが見分けにくくなることは、A-6 を作る時に扱う |
