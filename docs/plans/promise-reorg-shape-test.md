# 約束リストの新しい形のテストの計画（テスト担当向け）

この計画は、約束リストの新しい形の段 1 のテストを書くテスト担当のエージェントに渡す。テスト担当は、実装のコードを書き換えない。実装を読んで期待値を作らない。

前提として読むもの: `CLAUDE.md`、`docs/plans/promise-reorg-shape-impl.md` の 2 章と 3 章、`docs/plans/promise-reorg-layers.md` の 3 章（関係の表）、`docs/formats.md`、`docs/pitfalls.jsonl`。

この計画は、実装の計画がオーナーに承認されるまで、テスト担当に渡さない。

## テストの決まり

- テストの名前は日本語で、何を確かめているかを文で書く
- 一時の git のリポジトリは、テストごとの一時ディレクトリに作る
- 期待値は、実装の計画と `promise-reorg-layers.md` の表から作る。実装の出力から作らない
- 判定のテストを書いたら、対象の分岐をわざと壊して、テストが落ちることを確かめる
- ランダムなテストは、種を毎回変え、使った種を記録に出す
- 新しいテストを足す前に、同じ前提をたどる今のテストを探し、その拡張で済まないかを先に考える

## 確かめること

### 約束リストの形

| 確かめること |
|---|
| 性質・前提・仕様を、決まった項目で読める。決まっていない項目があれば、誤りになる |
| `[[claim]]` と、仕様の `subjects` は、決まっていない表・項目として誤りになる |
| 必須の項目（性質と前提の `id`・`statement`、機能と仕様の `refines`）がなければ、誤りになる。機能と仕様の `refines` が空でも、誤りになる |
| 性質に `[[property.evidence]]` を書くと、誤りになる |

### 関係の決まり

型の組は有限で小さいので、代表を手で選ばず、すべてを回す。

| 確かめること |
|---|
| `refines` の「書く側の型 × 指す先の型」のすべての組（性質・機能・仕様 × 性質・機能・仕様・用語・前提）で、許可された 3 つの組（性質→性質、機能→性質、仕様→機能）だけが通り、ほかは誤りになる |
| `assumes` の「書く側の型 × 指す先の型」のすべての組（性質・仕様・用語 × 性質・機能・仕様・用語・前提）で、指す先が前提の時だけ通る。機能に `assumes` を書くと、誤りになる |
| `refines`・`assumes` の指す先がなければ、誤りになる |
| 下に性質を持つ性質に、機能をつなぐと誤りになる。下に性質を持たない性質には、つなげる。性質が何段でも、同じ |
| 性質の `refines` が循環すると（自分自身、2 つの輪、3 つ以上の輪）、誤りになる |
| 1 つの機能が 2 つの性質を、1 つの仕様が 2 つの機能を `refines` できる |
| 同じ配列に同じ ID が 2 度あれば、誤りになる |
| 性質・前提の ID が、ほかの型の項目の ID と同じなら、誤りになる（型の組のすべて） |
| ランダムに作った項目の組で、2.2 の決まりを別に書いた判定（テストの中の、表から作った判定）と、チェックの結果が合う |

### 参照

| 確かめること |
|---|
| `{@id:<ID>}` が、性質と前提を指せる。画面では ID に置き換わる |
| 性質・前提の文の中の、指す先のない参照は、誤りになる |

### フィンガープリントと承認

| 確かめること |
|---|
| 性質・前提のフィンガープリントは、項目の順・空白・引用符の種類を変えても同じで、文を変えると変わる |
| 仕様のフィンガープリントは、`flags` と `guesses` を変えても同じで、`refines`・`assumes` を変えると変わる |
| 性質・前提を足す・変えると、承認のチェックが誤りにする。承認すると、通る。消すと、消したことへの承認を求める |
| 性質・前提の ID を変えると、新しいものとして承認を求める |
| `refines` で指された性質の文を変えても、指している機能の承認は失効しない。`assumes` で指された前提の文を変えても、指している仕様・用語・性質の承認は失効しない |
| 承認の記録の `kind` は、`spec`・`term`・`feature`・`property`・`truth`・`file` だけを受け付ける。`claim` は誤りになる |
| 画面から、性質と前提に承認でき、取り消せる。承認の記録とコミットのメッセージに、種類が正しく書かれる |

### アノテーション

| 確かめること |
|---|
| `@vanda:spec <ID>` が、仕様を指す。仕様でないものを指すと、誤りになる |
| `@vanda:claim` は、決まっていない種類として誤りになる（組み込みのアダプタのすべて） |
| 性質・前提を指す `@vanda:evidence` は、誤りになる |

### チェック・画面・API

| 確かめること |
|---|
| evidence-present は、仕様だけを見る。性質と前提に、エビデンスを求めない |
| 変わったものの一覧に、性質と前提が、漏れも重なりもなく出る（一覧の数の確かめが、新しい型でも働く） |
| 性質と前提の詳細に、文、理由（あれば）、`refines` と `assumes` の先、由来、承認の履歴が出る。機能と仕様の詳細に、`refines` の先が出る |
| API のパスと項目に、`claim` が残っていない |

### 言葉

| 確かめること |
|---|
| チェックの誤りの文と画面の文言に、仕様を指す「約束」が残っていない（「約束リスト」は除く）。「PO」「監督」が残っていない |

### 書き直した後の約束リスト

| 確かめること |
|---|
| vanda 自身の約束リストで、promise-list-shape と annotation-links が通る |
| 機能のすべてが、下に性質を持たない性質を 1 つ以上 `refines` している。仕様のすべてが、機能を 1 つ以上 `refines` している |
| 消える仕様を指すアノテーションが、残っていない |
| 承認の記録に、書き直す前の記録が残っていない |

### 消した機能

| 確かめること |
|---|
| vanda doctor と vanda version は、決まっていないコマンドとして誤りになる |
| 設定のバージョンが、動いている vanda と違えば、vanda check と vanda serve は止まる（今のテストが、消した後も通る） |

## 進め方

- 型の改名で通らなくなった今のテストを、新しい名前に直す。直す時に、確かめていることを変えない
- 部品ごとに報告する。実装が計画と違う時は、テストを実装に合わせず、報告する
