# 約束リストの作り直し: オーナーの行にガイドワードを当てた結果の草案

古い形の分析（逸脱の種類を、性質とガイドワードで並べると決める前のもの）。新しい形の分析は `promise-reorg-deviation-analysis.md` にあり、ここの抜けの番号（G1〜G12）を引き継いでいる。

オーナーが直すためのたたき台。制御図（`promise-reorg-control-structure.md`）のオーナーの指示（2・3・23 番）と、「人としたいこと」の A・B に、ガイドワード（`promise-reorg-guidewords.md`）を当てた。約束リストはまだ変えない。

- 「受け皿」は、上の側の約束の草案（`promise-reorg-upper-claims.md`）の ID。かっこの中は、根拠にした今の約束の ID
- 判定は、○＝受け皿がある、△＝受け皿はあるが足りない・決めることがある、✗＝受け皿がない、－＝当てはまらない
- 今の約束は、約束リストの文を読んで突き合わせた。コードは読んでいない

## 1. 抜けの候補のまとめ

受け皿のないもの（✗）と、足りないもの（△）のうち、損失の大きい順。

| # | 抜けの候補 | 出た所 | 損なわれる構成要素 |
|---|---|---|---|
| G1 | 承認の記録は、リポジトリの中のファイルに誰でも書き足せる。今の約束が確かめるのは記録の形だけで、vanda サーバーが書いたものか、名前の人が本当に承認したかは確かめない | 2 番「出て害になる」、B「信じられない」 | 真正性 |
| G2 | 承認できる人の決まりがない。git の user.name と user.email があれば、開発者（AI）を含む誰でも承認できる | 2 番「出て害になる」「残り続ける」 | 真正性、独立性 |
| G3 | 単体テストなどのファイルは、承認の対象ではない。テストの中身を弱めても、承認は失効せず、エビデンスは「揃っている」のままになる | B「できない」 | 証跡性 |
| G4 | 設定とチェックの設定は、承認の対象ではない。書き換えれば、チェックを外したり、承認の対象を減らしたりできる | B「できない」 | 真正性 |
| G5 | 約束を変えずにコードだけを変えた変更は、レビューの画面に何も出ない。その正しさを支えるのはエビデンスの実行結果だが、vanda は取り込んでいない | A「できない」 | 証跡性 |
| G6 | 画面の「揃っている」は、アノテーションがあるという意味。オーナーが「通った」「約束が守られている」と読み違えうる | A「読み違える」 | 証跡性 |
| G7 | オーナーが読む量についての約束がない。量が多いと、読まずに承認する | A「量が多すぎる」 | 完全性・十分性を人が判断できなくなる |
| G8 | マージした後に、誤った承認を取り消す方法がない。取り消せるのは今のブランチで書いた承認だけ | 3 番「出ない」、A「やり直せない」 | 追跡可能性 |
| G9 | 承認を取り消しても、承認の時に外したフラグ（AI 案・推測）は戻らない。取り消した後は、注意して読むべきものだと分からなくなる | 3 番「出て害になる」 | － |
| G10 | 別の PC で同時に承認した時に、承認の記録がどうなるかの約束がない（1 つの vanda サーバーの中の順番だけが約束されている） | 2 番「順序が違う」 | 追跡可能性 |
| G11 | 承認か取り消しが途中で失敗した時（記録は書いたがコミットできない、など）の扱いが、今の約束に見当たらない。上の側の約束の反証の条件にはある | 2・3 番「途中で止まる」 | 追跡可能性 |
| G12 | 開発者の確認内容の承認（23 番）は、まだない。受け皿になる約束は 1 つもない | 23 番のすべて | 証跡性、独立性 |

G3 と G4 は、今の約束 `check-agreement-targets` の文（承認の対象は、約束・用語・機能、シナリオテストかモデル検査のファイル、ガードレールのファイル）と、設定のファイルから読み取った。

| ガイドワード | そうなった形 |
|---|---|
| 出ない | 確認内容が承認されないまま、マージされる |
| 出て害になる | 開発者が確認していないエビデンスに、承認が付く |
| 出て害になる | 確認した人と承認した人が同じ（独立性がない） |

## 7. 手法について分かったこと

- 上の側の約束の草案 21 件は、今ある機能の正しさ（機能的）はよく受けている。○ の多くがこれに当たる
- 抜けは、真正性（G1・G2・G4）と証跡性（G3・G5・G6・G12）に集まった。どちらも、今の約束をまとめ上げる方法では出てこない
- 当てたのは、指示 3 行と、したいこと 2 行。書いた行は 71 で、そのうち受け皿のないものと足りないものが 34（まだない 23 番の 11 行を含む）
- 「人としたいこと」のガイドワードは、同じ抜けを指示の側と別の言い方で拾った（G1・G8・G12）。二重に当たるのは、抜けの見落としを減らす

## 8. G1〜G4 を、実装で試した結果

2026-11-23 に、リポジトリの写し（一時の場所）で、作ってある vanda を動かして試した。手を加えるたびにコミットし、`vanda check .vanda/checks/main.toml` の出力を比べた。

| # | したこと | 結果 | 起こせたか |
|---|---|---|---|
| G1 | 承認の記録に、`spec/Agreement.tla` の今のフィンガープリントと、いない人の名前（Nobody）を書いた記録を、手で書き足した | 「まだ承認していません」が 354 件から 353 件に減り、`spec/Agreement.tla` の行が消えた。コミットした人と記録の名前が違っても、何も知らせない | 起こせた |
| G2 | G1 と同じ（記録の名前は、誰のものでも受け入れられた） | 同上。vanda サーバーから、オーナーでない人や開発者（AI）が承認する操作は、試していない | 記録の側は起こせた。サーバーの側は試していない |
| G3 | アノテーションの付いた Go のテストのファイルで、最初のテスト関数の先頭に `return` を足し、中身が動かないようにした | 出力は 659 行のまま変わらず、evidence-present は「通った」のまま | 起こせた |
| G4 | チェックの設定（`.vanda/checks/main.toml`）から、agreement のチェックを消した | agreement の失敗（653 件）が出力から消え、終了コードが 0 になった。チェックの設定を変えたことは、`ci.toml` のチェックでも知らされない | 起こせた |

- G3 で `return` を足した関数が、アノテーションの付いた関数そのものかは確かめていない（同じファイルの最初のテスト関数）
- G4 は、チェックの設定で試した。設定（`.vanda/config.toml`）の `[[annotation]]` を消す形は試していない
