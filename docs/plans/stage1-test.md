# vanda 段 1 のテストの計画（テスト担当向け）

この計画は、vanda の段 1 のテストを書くテスト担当のエージェントに渡す。実装の計画（`docs/plans/stage1-impl.md`）は、別の開発者のエージェントに渡す。テスト担当は、実装のコードを書き換えない。実装を読んでテストの期待値を作らない（期待値は仕様から作る）。

前提として読むもの: `docs/spec.md`（機能の一覧と、データの形）、`docs/terms.md`（言葉）、`docs/plans/stage1-impl.md` の「段 1 で作るもの」と「作る部品」（何を作るかを知るため。作り方には頼らない）。

## テストの決まり

- テストの名前は日本語で、何を確かめているかを文で書く（例: `合意の後にフラグだけを立てると合意の審査で止まる`）
- 入力と期待値を、実装の都合から独立させる。期待値は、仕様（`docs/spec.md`）や手で作った例から用意する。実装が使うライブラリの出力から作らない
- 有限で小さい領域（エビデンスのタイプ 12、ステージ 5、アノテーションの種類 6、審査の範囲 2 など）は、代表値を手で選ばず、全部を回す
- 判定のテストを書いたら、対象の判定をわざと壊して（条件の反転、分岐の削除）、テストが落ちることを確かめる。落ちないテストは何も判定していない
- テストには、どの機能（`CMD-03` など）を確かめるかを書く。段 1 では vanda の約束リストはまだないので、アノテーション（`@vanda:evidence`）は付けない。約束リストを書いた後で付け直す

## テストの種類

| 種類 | 使う所 | 道具 |
|---|---|---|
| シナリオテスト | CLI の使い方そのもの（`vanda check`、`vanda doctor`）。人が読める台本にする | `testscript`（`.txtar`） |
| 単体テスト | 部品ごとの判定（指紋、アノテーションの読み取り、審査ごと） | Go の `testing` |
| ランダムチェック | 指紋が書き方の違いで変わらないこと、ID の重なりの判定など、入力が広いもの | `rapid` |
| クロスチェック | 合意の判定を、TLA+ のモデルと実装で比べる | TLC が作るトレース、または TLA+ のモデルを Go で読み直したもの（形は監督と相談して決める） |
| モデル検査 | 開発者が書く TLA+ のモデルの性質 | TLC（開発者が書く。テスト担当は、性質が空振りしていないか（どの動作も一度は起きるか）を確かめるテストを足す） |

## 確かめること

### 設定と版（CMD-01、CM-09）

| 確かめること | 例 |
|---|---|
| `version` が動いている vanda より新しいとき、エラーで止まり、上げるよう知らせる | |
| `version` が古いとき、エラーで止まり、移行のコマンドを知らせる | |
| `version` がないとき、エラーで止まる | |
| 設定のファイルがないとき、エラーで止まる | |
| 読むファイルのパターンが既定のとき、`.vanda/promises.toml` と `.vanda/agreements.toml` を読む | |
| パターンで複数のファイルに分けたとき、全部を読む | |

### 約束リストの形（CMD-10）

`docs/plans/stage1-impl.md` の「審査」の表の「約束リストの形」の 1 つずつについて、成り立つ例と破れる例を作る。特に:

| 確かめること |
|---|
| 約束に書いたレイヤーのどれかに、それを確かめるエビデンスがないと止まる |
| エビデンスの `layers` に、約束にないレイヤーを書くと止まる |
| `core = true` で `formal` を省くと、`formal = true` とみなされる |
| `core = true` かつ `formal = false` で `formal_waiver` がないと止まり、あれば通る |
| `core = false` なら、`formal` はどちらでも通る |
| 分けたファイルをまたいで ID が重なると止まる |
| `part_of` の循環で止まり、止まらずに回り続けない |

### 指紋（CM-03）

| 確かめること | 種類 |
|---|---|
| 約束リストの項目の順、空白、引用符の違いでは、指紋が変わらない | ランダムチェック |
| 文・理由・条件・対象・レイヤー・エビデンスのどれかを変えると、指紋が変わる | 全部の項目を回す |
| `flags` と `guesses` を変えても、指紋は変わらない | |
| ファイルの名前を変えただけなら、合意済のまま | |
| ファイルの中身を 1 文字変えると、提案中になる | |
| 約束の ID を変えると、提案中になる | |

### アノテーションの読み取り

| 確かめること |
|---|
| 6 つの種類それぞれを、Go・シナリオ・TLA+ のそれぞれで読める（組み合わせを全部回す。その言語で使わない組み合わせは、使わないことを確かめる） |
| Go では次の `func` の名前、シナリオではファイルの名前、TLA+ では次の定義の名前を読み取る |
| シナリオの冒頭のアノテーションは、ファイル全体に付く |
| 1 つのアノテーションに ID を 2 つ書くと、エラーになる |
| 読むファイルのパターンに当たったのに、アダプタが決まっていないと、審査で止まる |
| 外部のコマンドのアダプタが返した JSON を読める。形の誤った JSON や、コマンドの失敗は、エラーになる |

### 審査（CMD-03）

| 確かめること |
|---|
| 審査の設定のファイルを渡さないと、エラーになる |
| 範囲を「1 つのストーリー」にする審査を含むのに `--base` を渡さないと、エラーになる。範囲が全部の審査だけなら、渡さなくてよい |
| 設定に並べた順に審査が行われる |
| どれかの審査が失敗すると、終了コードが失敗になる |
| エラーのメッセージに、ファイル・行・何がいけないか・どう直すかがある |

### 合意（CMD-10）

テスト用の git のリポジトリを、テストの中で作って確かめる（実際のリポジトリに頼らない）。

| 確かめること |
|---|
| 合意していない約束があると止まる |
| 合意した後に中身を変えると止まる |
| 合意した後にフラグだけを立てると止まる |
| 同じ中身に、2 つのストーリーが別々に合意しても、合意済になる |
| ストーリー A が約束を変えて合意し、ストーリー B が変える前の中身に合意していたとき、B の範囲の審査は止まり、A の範囲の審査は通る。B が今の中身に合意し直すと通る |
| 範囲を「1 つのストーリー」にすると、ベースブランチから分かれた点より後に変わったものだけが対象になる |
| シナリオ、ガードレールの定義、オラクルの定義のファイルの中身を変えると、合意していなければ止まる |

### 由来、合意の記録の指す先、エビデンスが揃っている、読まれていないファイル

`docs/plans/stage1-impl.md` の「審査」の表の 1 つずつについて、成り立つ例と破れる例を作る。由来は、ベースブランチから分かれた点より前のコミットに ID がなくても止まらないことも確かめる。

## 進め方

1. 開発者の部品の報告を待たずに、仕様からテストを書き始めてよい。実装がまだない部品のテストは、失敗してよい
2. 書いたテストごとに、監督に報告する。報告には、確かめたこと、わざと壊して落ちることを確かめた判定、仕様から期待値を決められなかったことを書く
3. 仕様から期待値を決められないとき（仕様の曖昧さ）は、推測で決めず、監督に聞く
4. 実装のコード（テストのファイル以外）を書き換えない。プッシュはしない（監督が、PO の指示を受けて行う）
