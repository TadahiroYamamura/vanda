# vanda 段 2 の実装の計画（開発者向け）

この計画は、vanda の段 2 を実装する開発者のエージェントに渡す。テストの計画（`docs/plans/stage2-test.md`）は、別のテスト担当のエージェントに渡す。開発者は、テスト担当のテストを書き換えない。

前提として読むもの: `CLAUDE.md`、`docs/spec.md`、`docs/terms.md`、`docs/formats.md`（段 1 で決めた形。段 2 でも変えない。足すものは書き足す）。

## 段 2 で作るもの

GUI で、ストーリーで変わったものを見て合意できるようにする。段 2 が終わったら、vanda 自身で vanda を作る進め方に切り替える。

| 番号 | 機能 | 段 2 で作る範囲 |
|---|---|---|

| CM-06 | ベースブランチを画面で選ぶ | すべて。開いたときの既定は設定の値 |

## 作り

- `vanda serve` は、Go の `net/http` で API と画面のファイルを出す。画面のファイルは、React で作ったものを `go:embed` で埋め込む
- 画面は React と TypeScript で、`web/` に置く。作るのは Vite。作った結果（`web/dist/`）はコミットせず、`make build` が Node で作ってから Go をビルドする
- 処理（差分、合意の判定、指紋、審査）は Go の側にだけ書く。画面は API の結果を見せるだけにし、判定を持たない
- API は JSON。形は `docs/formats.md` に書く（v1.0.0 からは変えない取り決めではないが、画面とテストが頼るので書いておく）
- GitHub Issues は、`gh auth token` の値を使い、GitHub の REST API を `net/http` で呼ぶ（Go の依存は足さない）。どのリポジトリかは設定の `[story]` に書く
- 開発の道具（Node、pnpm、Playwright のブラウザ）は nix の flake に足す

## 作る部品

### 1. 差分と一覧（RV-01・02・05・10・13・14）

- ブランチごとの見方: ベースブランチと今のブランチが分かれた点の中身と、作業ツリーの今の中身を比べる（段 1 の審査と同じ比べ方を使う）
- ストーリー全体の見方: ストーリーの ID を持つコミットで変わったものすべての、ストーリーで最初に変える直前の中身と今の中身。途中で、ほかのストーリーが同じものを変えていたら示す
- 一覧の 1 件: 種類（約束・用語・機能・ファイル）、ID か場所、追加・変更・削除・名前の変更、合意の状態（提案中・合意済）、フラグ、変更前と変更後の中身
- 一覧は、同じものを 2 度出さない。一覧の数と、差分の数が合うことを、サーバーの側で確かめる
- 外れた合意（RV-14）は、段 1 の審査の判定を使って一覧に示す

### 2. 合意する（RV-06）

- 画面で 1 件ずつ合意する。合意すると、サーバーが、合意の記録を書き足し、その約束のフラグ（`flags`・`guesses`）を約束リストから外し、1 つのコミットにする
- 合意の記録を書くファイル: 設定の `agreements` の最初のファイル（既定は `.vanda/agreements.toml`）
- フラグを外すときは、約束リストのファイルのほかの行（コメント、空行、項目の順）を変えない
- コミットのメッセージ: `(chore) <ストーリーの ID> で <種類> <ID> に合意する`。ストーリーの ID を入れるので、由来の審査が通る
- 「誰が」は、git の `user.name` と `user.email`。設定されていなければ、合意できない旨を出す
- 作業ツリーに、合意と関係のない書きかけの変更があっても、それを巻き込まずにコミットする（合意で変えるファイルだけを足す）。合意で変えるファイルそのものに書きかけの変更があるときは、合意を断り、理由を出す

### 3. 約束の詳細（CL-01・02・04・05・07）

- エビデンスをタイプごとに: シナリオは本文、TLA+ は該当する定義（ファイル全体へのリンクも）、ガードレールは定義のファイル、Go のテストは名前とファイルの場所
- 由来: 約束が作られ・変わったコミットと、そのストーリーの ID
- 合意の履歴: 合意の記録のうち、その約束を指すもの（今の中身に合うか合わないかも）
- CL-07: TLA+ は、見せるときは数学の記号（`==` は `≜`、`/\` は `∧`、`\/` は `∨`、`~` は `¬`、`\A` は `∀`、`\E` は `∃`、`\in` は `∈`、`|->` は `↦`、`'` は `′` など）。コピーしたときはリポジトリの文字のまま。置き換えの表は `docs/formats.md` に書く

### 4. ストーリーの置き場所（CM-08）

- アダプタの受け渡しの形（段 1 の外部のアダプタと同じ作り）を決め、GitHub Issues のアダプタを vanda の中に持つ
- 段 2 で読むもの: 題、本文、添付ファイルへのリンク。ネットワークや認証の誤りは、画面にそのまま理由を出す（黙って空にしない）

### 5. 画面

- 画面の配置は、モックを参考にする（監督が別に渡す）。ただし、モックと `docs/spec.md` が食い違うところは、仕様を正とする
- ストーリーを選ぶ、ベースブランチを選ぶ、見方を切り替える、一覧、1 件の詳細と合意、約束の詳細へのリンク

## 決めてもらうこと（PO）

| # | 決めること | 推奨 |
|---|---|---|
| 1 | 合意のコミットの単位 | 1 件の合意ごとに 1 つのコミット。まとめる形にすると、画面の中に書きかけの合意を持つことになり、閉じたときに消えるおそれがある |
| 2 | E2E のテスト（Playwright）を CI のどこで動かすか | Linux だけ。macOS の CI では、nix で入れたブラウザが動かないことがあるため。macOS は Go と画面の部品のテストだけ |

## 進め方

段 1 と同じ（`docs/plans/stage1-impl.md` の「進め方」）。部品ごとに小さくコミットし、監督に報告する。計画にない判断は作る前に聞く。プッシュはしない。
