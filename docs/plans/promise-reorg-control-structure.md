# 約束リストの作り直し: vanda の制御図の草案

オーナーが直すためのたたき台。vanda を使った開発で、誰が、誰に、何を指示し、何が戻ってくるかを表にした。ガイドワード（`promise-reorg-guidewords.md`）を当てる対象の一覧として使う。約束リストはまだ変えない。

- 範囲は「vanda を使った開発」の全体。vanda の外部要素も、損失につながるので入れた
- 人の呼び方（オーナー、開発者、実装担当、テスト担当）は、約束リストの用語にまだない

## 1. vanda の境界

| 区分 | 基準 |
|---|---|
| 内部要素 | vanda がシンタックス・セマンティクス・プロトコルを定義するもの。約束の文の中身は含まない（人が決める） |
| インターフェース | 外部要素とやりとりする方法。外部要素が決めたシンタックスやプロトコルに従う部分 |
| 外部要素 | vanda が定義しないもの。vanda は約束できず、前提として書く |

vanda が意味を定義するのは、項目の種類（約束・エビデンス・承認が何か）、項目の中の欄、項目同士の関係、状態の決まり（どうなれば承認済か、どうなればエビデンスが揃っているか）まで。

| 区分 | 当てはまるもの |
|---|---|
| 内部要素 | 約束リスト・承認の記録・設定・チェックの設定の形と意味、アノテーションの書き方（公開）、Story: のトレーラー（公開）、CLI の呼び方と出力（公開）、API、アダプタを呼び出す手順（公開）、判定の処理 |
| インターフェース | アダプタの実装（組み込み・カスタム）、git の読み書き、ブラウザーとの HTTP のやりとり、端末とのやりとり |
| 外部要素 | コードとテストの中身、各言語の文法、git、ストーリーストア、ブラウザー、CI、人、AI のエージェント |

「（公開）」は、`docs/formats.md` に書く取り決め。内部要素だが、v1.0.0 からは変えない。

## 2. 人と道具

| 名前 | 中身 | 区分 |
|---|---|---|
| オーナー（人） | 約束を読み、承認するかを決める | 外部要素 |
| 開発者（人） | 設計を判断し、開発者（AI）に指示する。AI が書いたコードを直すこともある | 外部要素 |
| 開発者（AI） | AI のエージェント。約束リスト・コード・テストを書く | 外部要素 |
| CI | プッシュのたびに、テストと vanda check を動かすもの | 外部要素 |
| リポジトリ | git のリポジトリ。約束リスト、承認の記録、設定、コード、テストを持つ | 外部要素（持っている約束リスト・承認の記録・設定の形と意味は内部要素） |
| ストーリーストア | ストーリーを持つ外のサービス | 外部要素 |
| vanda check | チェックを順に動かし、終了コードと出力を返す命令 | 内部要素 |
| vanda サーバー | レビューの画面と API を出すもの | 内部要素 |
| アダプタ | アノテーションかストーリーを読み、vanda に答えるもの | インターフェース |

開発者の中に、実装担当（コードを書く）とテスト担当（テストを書き、アノテーションを付ける）がいる。人が AI の書いたコードを直す時は、その人が実装担当になる。表で「開発者」とだけ書いた行は、人でも AI でも、どちらの担当でも同じ。

## 3. 指示と、戻ってくる情報

「内部要素の関わり」が「なし（前提）」の行は、外部要素だけで閉じている。vanda は約束できないので、6 章の前提に書く。

「（まだない）」の行は、今の vanda にない指示。エビデンスを集めて保存する流れ（20〜23 番）は、証跡性と追跡可能性を担うので、損失を洗い出すために先に置いた。22・23 番は、エビデンスのタイプ「人のレビュー」にも同じ分担で当てはめる。24〜26 番は、層と関係の草案（`promise-reorg-layers.md`）で決めた操作。

| # | 指示する側 | 受ける側 | 指示 | 戻ってくる情報 | 内部要素の関わり |
|---|---|---|---|---|---|
| 1 | オーナー | ストーリーストア | ストーリーを書く | レビューの画面のストーリーの題・本文・添付 | なし（前提） |
| 2 | オーナー | vanda サーバー | 承認する | レビューの画面（変わったものの一覧、変更前と変更後、フラグ、エビデンスの予定と実際、承認の状態） | API、承認の記録、判定の処理 |
| 3 | オーナー | vanda サーバー | 承認を取り消す | レビューの画面（承認の状態、取り消せない理由） | API、承認の記録、判定の処理 |
| 4 | オーナー | 開発者 | フィードバックする（直しを頼む） | 直したコミットが、次のレビューで変わったものとして出る | なし（前提） |
| 5 | 開発者（人） | 開発者（AI） | 設計の判断を伝え、作業を指示する | 報告、コミット | なし（前提） |
| 6 | 開発者 | リポジトリ | 約束リストを書き換える（約束・用語・機能、エビデンスの予定、フラグ） | vanda check の出力 | 約束リスト |
| 7 | 開発者（実装担当） | リポジトリ | コードを書く | テストの結果、vanda check の出力 | アノテーションの書き方（センサーを付ける時だけ。コードの中身は外部要素） |
| 8 | 開発者（テスト担当） | リポジトリ | テストを書き、アノテーションを付ける | テストの結果、vanda check の出力 | アノテーションの書き方（テストの中身は外部要素） |
| 9 | 開発者 | リポジトリ | Story: のトレーラーを付けてコミットする | vanda check の出力 | Story: のトレーラー |
| 10 | 開発者 | リポジトリ | 設定・チェックの設定・CI の設定を書き換える | 承認の対象のファイルなら、レビューの画面に出る | 設定、チェックの設定（CI の設定は外部要素） |
| 11 | CI | テストなど | エビデンスを実行する（テスト、モデル検査など） | 実行結果 | なし（前提） |

| 13 | CI | リポジトリ | マージを通す・止める | マージされたか | なし（前提） |

| 15 | vanda check・vanda サーバー | アダプタ | アノテーションを読ませる | アダプタの答え | アダプタを呼び出す手順（アダプタの実装はインターフェース） |
| 16 | vanda サーバー | ストーリーストア | ストーリーを読む（トークンを送る） | ストーリーの題・本文・添付、エラー | アダプタを呼び出す手順（アダプタの実装はインターフェース） |
| 17 | 開発者 | vanda init | .vanda/ を作る | 端末の質問と出力 | CLI の呼び方と出力、設定（端末とのやりとりはインターフェース） |

| 25 | オーナー | vanda サーバー | 開発者の十分性の確認内容を承認する（まだない） | レビューの画面（上の層の項目、下の層の項目の組、承認の状態） | API、承認の記録、判定の処理 |
| 26 | オーナー | vanda サーバー | 承認を失効させる（まだない） | レビューの画面（承認の状態） | API、承認の記録、判定の処理 |

## 4. インターフェースを通るもの

規範的な損失のガイドワードを当てる対象。

| # | 通るもの | どこから、どこへ |
|---|---|---|
| a | ブラウザーからのリクエスト | ブラウザー（ほかのサイトのページを含む）から vanda サーバーへ |
| b | ストーリーストアのトークン | vanda サーバーからストーリーストアへ |
| c | ストーリーの題・本文・添付 | ストーリーストアからレビューの画面へ |
| d | アダプタの答え | カスタムアダプタ（リポジトリの中のプログラム）から vanda へ |
| e | 承認の記録 | 承認した人の PC から、リポジトリを通して CI へ |
| f | 承認する人の名前 | git の設定から承認の記録へ |

## 5. 人としたいこと

目的的な損失のガイドワードを当てる対象。

| # | 人 | したいこと |
|---|---|---|
| A | オーナー | ソースコードを読まずに、ストーリーで変わったことが正しいかを判断する |
| B | オーナー | 承認したものが、後から黙って変わっていないと信じる |
| C | 開発者 | 何が足りなくてチェックが通らないかを知り、直す |
| D | 開発者 | 手で直さずに、vanda を使い始める |
| E | 開発者 | 組み込みのアダプタにない言語・ストーリーストアを vanda につなぐ |

## 6. 前提（外部要素について、vanda が約束できないこと）

成り立たないと Accountability が切れる。vanda を使う側が、自分で確認する。

| 元の行 | 前提 |
|---|---|
| 1 | ストーリーが、ストーリーストアに書かれている |
| 4 | オーナーのフィードバックが、開発者に伝わる |
| 5 | 開発者（人）の設計の判断が、開発者（AI）に伝わる |
| 10 | CI の設定が、承認なしに書き換えられない |
| 11 | CI がエビデンスを実行し、落ちたらマージを止める |
| 13 | vanda check が失敗したら、マージが止まる |
| 14 | git と、リポジトリを置くサービスが、履歴を正しく保つ |

## 8. 入れなかったもの

- vanda のビルドと配布（使っている vanda が、約束を満たした vanda と同じものか）
- 複数のオーナーがいる時の、オーナーの間の分担
- 移行のコマンド（まだない。作る時に行を足す）。約束リストと承認の記録を書き換えるので、承認とフィンガープリントの結びつきをどう保つかを、その時に決める

## 9. 書きながら気づいた所

- 4 番と 5 番: 人から開発者（AI）への指示は、開発を動かす主な指示だが、vanda の内部要素が関わっていない。前提のままでよいかは、ガイドワードを当てる時に見る
- 10 番: チェックの設定を書き換えれば、チェックを弱められる。チェックの設定が承認の対象のファイルになっているかは、未確認
- 11 番と 12 番: vanda は実行結果（通ったか）を取り込んでいない（`docs/spec.md` の CM-04 がまだ作られていない。20・21 番）。エビデンス完備のチェックが見るのは、約束を指すアノテーションがあることまで。エビデンスが「ある」ことと「通った」ことをつなぐのは、今は 6 章の前提（11 番）だけ
- 22 番と 23 番: エビデンスが約束を支持しているかを人が確認した記録は、今はどこにも残らない。エビデンスのタイプ「人のレビュー」も、行ったかを vanda は確認していない（`docs/formats.md` で「確かめない」）
- f: 承認する人の名前は git の設定のままで、本人確認をしていない。開発者（AI）がオーナーの名前で承認できるかは、未確認
