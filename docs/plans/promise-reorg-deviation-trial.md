# 約束リストの作り直し: 性質にガイドワードを当てる試しの結果

性質向けのガイドワードで逸脱の種類を並べる方法（`promise-reorg-properties.md` の 5 章）が使えるかを、性質 2 つで試した。約束リストはまだ変えない。

## 1. 結論

- vanda が主語の性質（A-2 完全性）でも、抜けが見つかった。書いた 19 行のうち、今の分析（`promise-reorg-analysis-owner.md`）の抜けを見つけ直したものが 9 行、新しい抜けの候補が 4 行、対策があったものが 5 行、前提に当たるものが 1 行
- まだ何も作っていない性質（B-1 想定）では、抜けは見つからない（すべて対策なしになる）。ただ、出てきた逸脱の形は、作る時の大まかな反証の条件の元になる
- 4 つの条件のうち、「原因まで辿れる」と「約束リストに戻せる」は、升目ごとにほとんど変わらなかった。そこで、逸脱の形ごとに見るのは「早く検知される」と「被害が致命的にならない」の 2 つとし、残りの 2 つは性質ごとに 1 回見ることにした
- 升目 1 つに、逸脱の形が 2〜5 個出た。逸脱の種類を「性質とガイドワードの組み合わせ」とすると、1 つの升目に対策のあるものとないものが混ざる。そこで、答責性の実現度は、逸脱の形を単位に数えることにした（`promise-reorg-properties.md` の 5 章）

## 2. 試したガイドワード

性質の文が暗に置いている前提を、1 つずつ外す問い。

| ガイドワード | 外す前提 | 問い |
|---|---|---|
| 対象から外れている | 対象の範囲 | この性質が及ばないものは何か |
| 想定していない行為者が行う | 行う人 | 想定した人でない行為者が行ったら、どうなるか |
| 仕組みを通らない | 通る道 | vanda を通らずに、同じ結果を作れるか |
| 満たされているように見える | 見え方 | 満たされていないのに、満たされていると読めるか |
| 量が増えると崩れる | 量 | 件数や人数が増えた時にも成り立つか |
| 後から崩れる、元に戻せない | 時点 | 一度満たされた後に崩れるか。崩れた時に戻せるか |
| 途中で止まる | 最後まで終わる | 途中で止まった時、半分だけ満たされた状態が残るか |

「途中で止まる」は、試しの後に足した。初めの 6 つからは、G11（承認が途中で止まる）が自然に出てこなかったため。

## 3. A-2 完全性: 承認されていない変更があれば、vanda のチェックは通らない

- 判定は、○＝対策がある、△＝一部ある・確かめていない、✗＝対策がない
- 「検知」は早く検知される、「限定」は被害が致命的にならない
- 「出どころ」の G は、今の分析の抜けの番号。「新」は、この試しで出た候補

| ガイドワード | 逸脱の形 | 検知 | 限定 | 出どころ |
|---|---|---|---|---|
| 対象から外れている | 単体テストなどのファイルを変えても、承認は要らない | ✗ | ✗ | G3（実装で起こせた） |
| 対象から外れている | 設定・チェックの設定を変えても、承認は要らない | ✗ | ✗ | G4（実装で起こせた） |
| 対象から外れている | CI の設定（`.github/workflows/check.yml`）を変えて、vanda check を呼ばなくしても、承認は要らない | ✗ | ✗ | 新 |
| 対象から外れている | 約束リストを変えずにコードだけを変えた変更は、承認の対象にならない | △ テストは流れるが、vanda は結果を知らない | ✗ | G5 |
| 対象から外れている | チェックに使う vanda そのものを変えても、承認は要らない（このリポジトリでは、同じ変更の中で作った vanda が、自分をチェックする） | ✗ | ✗ | 新 |
| 想定していない行為者が行う | オーナーでない行為者が、承認の記録を書く | ✗ | ✗ | G1・G2（実装で起こせた） |
| 想定していない行為者が行う | チェックを通さずにマージできる行為者（管理者、hotfix）がマージする | ○ `main` への push で、スコープ all のチェックが動く（マージの後） | ✗ | 前提。検知の対策は見つけ直した |
| 仕組みを通らない | 承認の記録に、手で書き足す | ✗ | ✗ | G1（実装で起こせた） |
| 仕組みを通らない | CI が渡す比べる元（`--base`）を新しいコミットにして、承認のチェックの範囲を狭める | △ `main` への push のチェックで、後から分かる | ✗ | 新（下の「確かめたこと」） |
| 仕組みを通らない | Story: のトレーラーのないコミットで変える | ○ story-origin のチェック | ○ マージの前に止まる | 対策あり |
| 満たされているように見える | 出力に「通った」が並ぶが、承認のチェックが設定から外れている | ✗ | ✗ | G4 |
| 満たされているように見える | 作業ブランチでチェックの失敗が続き（今は 653 件）、新しい失敗が件数に埋もれる | △ 1 件ずつ出力には出る | ✗ | 新 |
| 量が増えると崩れる | 未承認が数百件たまり、読まずにまとめて承認する | ✗ | ✗ | G7 |
| 量が増えると崩れる | 2 つのストーリーが同じ項目を変え、取り込んだ後の中身を誰も承認していない | ○ フィンガープリントが変わり、承認済でなくなる | ○ マージの前に止まる | 対策あり |
| 量が増えると崩れる | 別の PC で同時に承認し、承認の記録がぶつかる | △ 約束がない | ✗ | G10 |
| 後から崩れる、元に戻せない | 承認の後に、中身が変わる | ○ フィンガープリント | ○ マージの前に止まる | 対策あり |
| 後から崩れる、元に戻せない | マージの後に、誤った承認に気づく | － | ✗ 取り消せない | G8 |
| 後から崩れる、元に戻せない | vanda のバージョンが上がり、フィンガープリントの作り方が変わる | ○ 今の中身に合う承認の記録がなくなり、未承認の側に倒れる（推論。試していない） | ○ チェックが通らない | 対策あり（残るのは、すべてを承認し直す手間） |
| 途中で止まる | チェックの途中で入力が読めなくなり、残りのチェックが行われないまま、通ったように終わる | ○ 読めない入力に頼るチェックを、失敗にする | ○ 終了コード 1 で終わる | 対策あり |

残りの 2 つの条件は、升目によらず、ほぼ同じだった。

| 条件 | A-2 での対策 |
|---|---|
| 原因まで辿れる | ○ git の履歴と Story: のトレーラーで、どの変更で入ったかは辿れる。ただし、承認の記録の名前は確かめられていないので（G1）、「誰が承認したか」は △ |
| 約束リストに戻せる | ✗ 見つかった逸脱を約束リストに戻すための、vanda の支えはない（B-3 の上向きの経路が、まだない） |

### 確かめたこと

- `--base` を 1 つ前のコミットにすると、スコープ story の承認のチェックの失敗は、653 件から 18 件に減った（残った 18 件は、失効した承認）。今のコミットにすると、ストーリーが分からないというエラーで止まった
- 今のブランチでは、`main.toml` も `ci.toml` も、終了コード 1 で終わる（未承認が 653 件あるため）

### 確かめていないこと

- 「新」の 5 件のうち、実物で試したのは `--base` だけ。CI の設定、vanda そのもの、バージョンの 3 件は、設定と約束の文から読み取った
- `main` への push のチェックが、チェックを通さないマージを実際に見つけるかは、試していない

## 4. B-1 想定: vanda は、起こりうる逸脱を抜けなく想定するための手がかりを、仕様を書く人と十分性を確認する人に渡す

今の vanda には、この性質を実現する機能がない。升目はすべて「対策なし」になるので、判定は書かない。出てきた逸脱の形を、作る時の大まかな反証の条件の元にする。

| ガイドワード | 逸脱の形 |
|---|---|
| 対象から外れている | 手がかりが、一部の性質にしか使えない（例: 人が主語の性質には当てられるが、前提や用語には当てられない） |
| 対象から外れている | レッドチームが見る範囲が、画面や CLI だけで、承認の記録や設定のファイルを見ない |
| 想定していない行為者が行う | 逸脱の種類を並べるのも、対策が「ある」と付けるのも開発者（AI）で、人が読まない |
| 想定していない行為者が行う | 逸脱の種類を並べた行為者と、レッドチームが同じ |
| 仕組みを通らない | 手がかりを使わずに仕様を書き、十分性を「確認した」と記録する |
| 満たされているように見える | 升目はすべて埋まっているが、多くが「当てはまらない」で埋めただけ |
| 満たされているように見える | 対策が「ある」と付いているが、わざと逸脱を起こすと検知されない |
| 量が増えると崩れる | 升目が多すぎて、読まずに埋める・読まずに承認する |
| 量が増えると崩れる | 性質が増えるたびに升目が増え、古い升目を見直さなくなる |
| 後から崩れる、元に戻せない | 性質や機能が変わった後も、古い逸脱の種類の一覧が残る |
| 後から崩れる、元に戻せない | レッドチーミングを 1 度しただけで止まり、外の逸脱の推移が取れない |

## 5. 方法について分かったこと

| 分かったこと | 中身 |
|---|---|
| vanda が主語の性質でも見つかる | A-2 で、新しい候補が 5 件出た。「対象から外れている」と「仕組みを通らない」が、最もよく見つけた |
| ガイドワードどうしが重なる | 「承認の記録に手で書き足す」は、「想定していない行為者が行う」と「仕組みを通らない」の両方に出た。重なりは、見落としを減らすが、同じ抜けを 2 度数える |
| 答えるには、今の vanda を知っている必要がある | 「対象から外れている」の 5 行は、承認の対象の決まり（`check-agreement-targets`）と CI の設定を読んで、初めて書けた |
| 「対象から外れている」は、想定の範囲の外を拾う | A-2 の 5 行は、承認の対象に入っていないもの。A-2 は今想定できている範囲についての性質なので、これらは A-2 の文の誤りではなく、範囲を広げる候補として扱う |
| 条件の 2 つは、升目ごとに変わらない | 「原因まで辿れる」「約束リストに戻せる」は、性質ごとに 1 回見れば足りる |
| まだない性質には、判定が付かない | B-1 のように機能がない性質は、すべて対策なしになる。そこで、機能がない性質は答責性の実現度の分母に入れず、その数を別に見せることにした。逸脱の形は、機能を作る時の反証の条件の元として残す |
| かかった手間 | 性質 1 つに、逸脱の形が 11〜18 行。16 の性質すべてなら、200〜300 行になる見込み |
