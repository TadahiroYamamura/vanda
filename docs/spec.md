# vanda の仕様

まだ作っていない機能と、その範囲を書く。作った機能の用語・機能・振る舞い（約束）とその理由は、約束リスト（`.vanda/promises.toml`）にある。機能を作ったら、約束リストに書き、ここから消す。

## 置き場所と版

- vanda の版が上がったら、移行のコマンドで `.vanda/` の中身を新しい形に書き換える。版が上がったときは、`.vanda/` の中だけ変えれば対応が終わるようにする。形の版は別に持たない（移行は vanda の版ごとに決まる）
- `.vanda/` の外にあって vanda が読むもの（アノテーションの書き方、CI からの CLI の呼び方）は、版が上がっても変えない
- 後方互換を約束するのは v1.0.0 から



| 読み手 | 使うもの | 目的 |
|---|---|---|
| PO | GUI | 機能を決め、リリースの順番と方法を決める（前提、事前の準備、問題が起きたときの対応）。約束を合意する（当面） |
| Dev | GUI | 機能の詳細を詰め、証跡を確かめる |
| QA | GUI | 品質基準を作って見直し、品質を保ち、進め方を改善する |
| 監査 | エクスポートした頁 | 誰がいつ何を合意し、何で確かめたかを後から追う |

範囲の外: PM（開発状況の俯瞰と遅延の把握。CI を通じて別のツールに連携する）、アーキテクト（要るなら別のツール）、運用・サポート（約束リストなどの Markdown を AI が読む）、業務の担当者（PO や Dev が確かめに行く）。

### AG エージェント

vanda は、実装する AI エージェントを tmux のセッションで起動し、待っているエージェントを tmux に 1 文を打ち込んで起こす。エージェントのセッションの終了と再開は作らない（どのストーリーでどのセッションを使うかを別に管理する必要があり、今は要らない）。

エージェントの状態（ストーリー・ブランチ・エージェントの設定の名前・tmux のセッションの結びつき、状態、活動、待っている質問）は、vanda の手元のデータの置き場所（例: `~/.local/share/vanda/`）に、リポジトリごとの小さな DB として持つ。人ごと・マシンごとの状態で、チームで共有しないので、リポジトリには入れない。

| 番号 | 機能 | 関係 |
|---|---|---|
| AG-01 | ストーリーごとに、エージェントの状態を示す（作業中 / 待機中（理由: レビュー待ち・質問への回答待ち・入力待ち（コンソール））/ 止まった / 終わった） | |
| AG-02 | 待機中になったら、ブラウザの通知と通知音で知らせる。どの画面にいても、待機中の数が分かる | |

#### アノテーション

書き方と読み方は作った（約束リストと `docs/formats.md`）。`.vanda/` の外にあり、v1.0.0 からは書き方を変えない。

#### 読み下し（RV-15）

- 読み下しは定義ごとに持ち、変わった定義の分だけ作り直す（作り直すと、変わっていない定義の言い回しまで変わり、差分が広がるため）

#### 実行の結果

| 項目 | 必ずか |
|---|---|
| エビデンスの名前（アダプタが読み取った名前） | 必ず |
| 合格・不合格・飛ばした（飛ばしたものは不合格と同じに扱う） | 必ず |
| 日時 | 必ず |
| 版（コミット） | 必ず |
| 実行した環境（CI、本番の監視など） | 必ず |
| かかった時間 | あってもよい |
| 添付 | あってもよい |

添付は、実行の結果に付ける汎用の仕組み。1 件ごとに次を持つ。

| 項目 | 中身 |
|---|---|
| 名前 | その結果の中で重ならない名前。添付を名前で参照する（例: `trace-seed-1`、`trace-seed-2`） |
| 種類 | 見せ方を決める。vanda が決めた種類（`log`、`failure`、`trace`、`model-check-stats`、`input-stats`、`decoy-report`、`guardrail-trials` など）は、決めた形で書けば GUI が専用の見せ方をする。それ以外は、ふつうの添付として見せる |
| 中身の形 | JSON、テキスト、画像など |
| 中身 | 中身そのものか、中身へのリンクのどちらか（制限のある環境では、リンクだけにできる） |

- 名前と種類を分けるので、同じ種類の添付を複数付けられる（例: トレースを複数）
- 実行の記録（種類 `trace`）の形: 1 つの `trace` は、種（シード値）と操作の列の一覧を持つ。1 本の操作の列は、列の番号、終わり方（成功・エラー・食い違い）、操作の一覧を持つ。1 つの操作は、操作の名前、入力の値、オラクルの結果、実装の結果、一致したかを持つ。ランダムチェックでは、オラクルの結果の代わりに、性質を満たしたかを持つ。値はそのまま書き、長い値の省略は GUI の側で行う。細かい項目の名前は、vanda を作るときに決める
- 実行の結果と添付の保管の期間は、vanda では決めず、取ってくる元（CI の成果物、ファイルサーバーなど）の設定に任せる。vanda は、今の版の最新の結果があることだけを求め、古い結果が消えていても困らないようにする
- vanda が決めた種類と、その中身の形は、`.vanda/` の外の取り決めなので、v1.0.0 からは変えない

#### 制限のある環境の実行の結果

本番の DB との一致のように、開発者が入れない環境で動かすエビデンス（運用のステージの監視など）は、その環境の側の人や仕組みが動かし、結果を取ってくる元（CM-04）に置く。リポジトリには書き込まない。

- 実行の結果で vanda が必ず求めるのは、合格か不合格か、日時、版だけ。ログや食い違いの中身は、なくても扱える
- 食い違いの中身やログは、その環境の側に置く。結果には、その環境の側の仕組みへのリンクだけを入れてよい（開くには、その環境の権限が要る）
- 何を渡すかは、結果を作る環境の側の人（管理者）が決める
- 開発者の手元の vanda に届くのは、開発者がもともと知っている合意した中身と、その環境が一致しているかの判定だけになる

#### ストーリーの記録

根拠・判断・阻害要因（RV-09）は、ストーリーの置き場所に、人が読む本文と機械が読む情報を 1 つのコメントにして書く。

- vanda は、1 つの記録から両方を作る。正は機械が読む情報で、本文はそこから作った表示とみなす
- 機械が読む情報には、種類、対象の ID と部分、ストーリーの ID、vanda の記録の ID、本文の指紋を入れる
- 読み戻すときに本文の指紋が合わなければ、「置き場所の上で書き換えられた」と GUI に出す。人が、vanda で記録し直すか、元に戻すかを選ぶ。記録が見つからなくなったら、そのことを GUI に出す
- 埋め込み方は、置き場所のアダプタが決める。GitHub Issues 以外（Jira、Backlog、Redmine など）にも、アダプタを足して使える
- 置き場所を乗り換えるときは、前の置き場所のアダプタで記録を読み戻し、新しい置き場所のアダプタで書き直せるようにする

#### 設定

`.vanda/config.toml` に、まだ書けないもの（版・ファイル・レイヤー・アノテーション・ガードレール・ストーリー・GUI の項目と、審査の設定は作った）:

| 区分 | 項目 |
|---|---|
| 実行の結果 | 取ってくる元（環境ごとに複数）と、そのアダプタ。結果の変換のアダプタ（テストを動かす道具ごと） |
| エージェント | 名前付きのエージェントの設定を、いくつでも書く。それぞれに、使うエージェントのアダプタ、起動のコマンド、引数、環境の変数、モデルなど。起動するときに名前を選ぶ（例: `vanda agent start --story 24 --agent codex`）。どの場面でどれを使うかは、プロジェクトの規則で決める |

設定に書かないもの: 通知の音などの人ごとの好み（GUI の側で持つ）。

環境の変数は、GUI とエージェントが起動したときのものが使われ、後から変えても効かない（変えたら起動し直す）。認証は、使うたびに読めるもの（`gh` のログインなど）をできるだけ使う。GUI でも、今どの設定で動いているかを CMD-01 と同じく確かめられるようにする。

#### アダプタ

5 種類のアダプタを、同じ作りで用意する。アノテーションの読み取りと、ストーリーの置き場所の読むところ、ガードレールの定義の取り出しの「ファイルを読むだけ」のアダプタと、`.vanda/adapters/` のアダプタは作った。

| アダプタ | 受け取るもの | 返すもの |
|---|---|---|
| 実行の結果の変換（CMD-02） | テストを動かす道具の出力（`go test -json`、JUnit の XML など） | vanda の形の実行の結果 |
| ガードレールの定義の取り出し（ファイルを読むだけのほか） | プロジェクト（マイグレーションなど） | 今効いている定義（DB なら、空の DB にマイグレーションを当てた結果の構造） |
| ストーリーの置き場所（CM-08）の書くところ | 書く記録 | コメント、読み戻した記録。記録を人が読む本文と機械が読む情報にして、置き場所に書く・読み戻す（埋め込み方は置き場所ごとに決める。GitHub なら HTML のコメント） |
| エージェント（CMD-06） | エージェントの設定 | エージェントの種類（Claude Code、Codex など）ごとの違いを吸収する。MCP とフックの渡し方、起こすときに打ち込む文、中断のキー |

- vanda は、`go test -json` と TLC の出力のアダプタを組込みで持つ
- アダプタとの受け渡しの形は `.vanda/` の外の取り決めなので、v1.0.0 からは変えない

#### エビデンスのタイプ

約束リストのエビデンスの `type` に書く値。一覧は vanda が決める。値は、日本語の言葉をそのまま英語にし、単語を `-` でつなぐ。

| タイプ | 値 | 確かめること | 実行できるか |
|---|---|---|---|
| モデル検査 | `model-check` | 決めた範囲の中のすべての状態をたどって、性質が成り立つ（TLC） | できる |
| 証明 | `proof` | すべての値で、性質が成り立つ（Dafny） | できる |
| クロスチェック | `cross-check` | オラクルと実装に同じ操作を送り、結果を比べる | できる |
| ランダムチェック | `random-check` | 無作為な入力で、性質を確かめる | できる |
| シナリオテスト | `scenario-test` | シナリオ（CLI のコマンドの並びの台本）を動かして確かめる | できる |
| 単体テスト | `unit-test` | — | できる |
| インターフェースのテスト | `interface-test` | DB や CLI などの境界の振る舞い。どのレイヤーかは、エビデンスのレイヤーで表す | できる |
| 同時実行のテスト | `concurrency-test` | — | できる |
| ガードレール | `guardrail` | 拒むべきものを試し、拒まれる | できる |
| センサー | `sensor` | 実装の中で事後条件を確かめる | — |
| 監視 | `monitoring` | 動いているものを見張る | — |
| 人のレビュー | `human-review` | 人が読んで確かめる | — |

#### 審査の種類（CMD-10）

まだ作っていない審査を書く（約束リストの形・アノテーションのつながり・由来・合意・合意の記録の指す先・エビデンスが揃っている・読まれていないファイルの審査は作った）。

自然言語だけの約束どうしの矛盾は、審査の種類に入れない。AI の点検は結果が揺れ、誤った指摘で止まると直すものがないため。合流の前に AI に点検させ、見つけたものを阻害要因として人に出す。

審査は、どれも失敗したら止める（「知らせるだけ」の段は設けない）。どの審査も、失敗したら直せる形にする。実行しない審査は、設定のファイルに書かない。

| 区分 | 審査 | 範囲 |
|---|---|---|
| エビデンス | 実行できるもの（テスト、シナリオ、オラクルの検査、ガードレールの試し）は、今の版での実行の結果があって合格している。結果がないものは不合格と同じに扱う。実行しないもの（人のレビュー、監視など）は、予定したもの（読むファイルなど）がある（予定したエビデンスが揃っているかは作った） | 全部か、1 つのストーリーで変わったもの |
| キャッチしない理由 | キャッチしないデコイのそれぞれに、理由の種類と理由の文がある | 全部 |
| モデル検査 | モデル検査（TLC）が通り、どの動作も一度は起きる（矛盾した約束による空振りを見つける）。並行するストーリーの矛盾を見つけるには、合流した後の状態で動かす（どの状態で動かすかは CI の設定で決める） | 全部 |
