# vanda の仕様


## 置き場所と版

- vanda が扱うデータ（設定、審査の設定、合意の記録、約束リスト）は、すべてリポジトリの `.vanda/` に置く。エビデンスの本体（オラクルの TLA+、シナリオ、DB の構造など）は、プロジェクトの作りに合わせた場所に置き、約束リストから指す
- `.vanda/` に形の版を持たせ、vanda の版が上がったら、移行のコマンドで中身を新しい形に書き換える。版が上がったときは、`.vanda/` の中だけ変えれば対応が終わるようにする
- `.vanda/` の外にあって vanda が読むもの（アノテーションの書き方、CI からの CLI の呼び方）は、版が上がっても変えない
- 使う vanda の版を `.vanda/` の設定に書き、チームで揃える
- `.vanda/` のファイルは、設定（`.vanda/config.toml`）、約束リスト（既定は `.vanda/promises.toml`）、合意の記録（既定は `.vanda/agreements.toml`）、審査の設定（`.vanda/checks/<名前>.toml`）。約束リストと合意の記録は、設定に読むファイルやパターン（例: `promises = [".vanda/promises/*.toml"]`）を並べて、複数のファイルに分けられる。TOML に読み込みの命令はないので、独自の命令は作らない。`.vanda/` にあるのに読まれていないファイルは審査で止める
- 後方互換を約束するのは v1.0.0 から
- `.vanda/config.toml` の `version` に、使う vanda の版を書く。動いている vanda が古ければエラーにし、上げるよう知らせる。新しければ、移行のコマンドで `.vanda/` を書き換えるよう知らせ、書き換えるまではエラーにする。形の版は別に持たない（移行は vanda の版ごとに決まる）



| 読み手 | 使うもの | 目的 |
|---|---|---|
| PO | GUI | 機能を決め、リリースの順番と方法を決める（前提、事前の準備、問題が起きたときの対応）。約束を合意する（当面） |
| Dev | GUI | 機能の詳細を詰め、証跡を確かめる |
| QA | GUI | 品質基準を作って見直し、品質を保ち、進め方を改善する |
| 監査 | エクスポートした頁 | 誰がいつ何を合意し、何で確かめたかを後から追う |

範囲の外: PM（開発状況の俯瞰と遅延の把握。CI を通じて別のツールに連携する）、アーキテクト（要るなら別のツール）、運用・サポート（約束リストなどの Markdown を AI が読む）、業務の担当者（PO や Dev が確かめに行く）。

## 画面

## 機能

管理番号は `<画面の ID>-<2 桁の番号>`。画面をまたぐものは `CM`、CLI は `CMD`。番号は使い回さない（消した機能の番号は欠番にする）。

### CM 共通

| 番号 | 機能 | 関係 |
|---|---|---|
| CM-01 | 手元のサーバーを起動し、ブラウザで開く（自分のマシンの中でだけ開く） | |
| CM-02 | 約束リストを読む | |
| CM-03 | 合意の記録（約束リストとは別のファイル）を読み書きする。約束ごとに、合意したときの中身の指紋・日付・ストーリーの ID を持つ | |
| CM-04 | エビデンスの実行の結果（日時、コミットか版、通ったか、ログ）を取り込む。取ってくる元を差し替えられる（GitHub Actions の成果物、ファイルサーバー、手元のパスなど）。結果のファイルの形は vanda が決める | |
| CM-05 | git の履歴から、約束ごとの由来を作る。由来は、約束が作られ・変わった履歴で、1 件ごとに、ストーリーと、そのきっかけになった判断（RV-09 の記録）を結ぶ。コミットのメッセージの中のストーリーの ID の書き方（`#24`、`PROJ-123` など）は、置き場所ごとに決める | |
| CM-06 | 比べるベースブランチを、画面でその場で選ぶ。今どのベースブランチと比べているかを常に示す。画面を開いたときの既定は、設定（CM-09）に書いたベースブランチ | |
| CM-07 | 検索と絞り込み（エビデンスのタイプ、レイヤー、コア機能か、合意の状態） | |
| CM-08 | ストーリーの置き場所と連携する。置き場所を差し替えられる（GitHub Issues、Jira、Backlog、Redmine など）。vanda が求めるのは、ストーリーの ID・題・本文・コメント・添付ファイルを読むことと、コメントを書くことだけ。最初は GitHub Issues の分だけを作る | |
| CM-09 | 設定をテキストのファイル（例: リポジトリの直下の `vanda.toml`）で持つ。約束リストと合意の記録の場所、ストーリーの置き場所と ID の書き方、エビデンスの実行の結果を取ってくる元を書く。画面で書き換える機能は作らない。認証の鍵はファイルに書かず、環境の変数や、すでにある道具の認証（`gh` のログインなど）を使う | |

### RV ストーリーのレビュー

| 番号 | 機能 | 関係 |
|---|---|---|
| RV-01 | ストーリーで追加・変更・削除されたものの一覧を示す。対象は、約束リストの項目（約束・用語・機能）と、エビデンスの本体（シナリオ、ガードレールの定義（DB の制約なら SQL）、オラクルの定義）。漏れも重複もない（比べる元（CM-06）と今のあいだで、追加・変更・削除されたものが、すべて、1 度ずつ出る。それ以外は出ない）。約束の文が変わらず、エビデンスの本体だけが変わったものも出る。提案中の案も含める | |
| RV-02 | 通し番号と総数を示す | |
| RV-03 | 欠番（既読の管理はしない。2026-10-31） | |
| RV-04 | 注意して読む手がかりとして、フラグを立てる。フラグは「AI 案」（AI が自分で決めたもの）・「推測」（推測を含むもの）・「差分あり」（前の合意から中身が変わったもの）。フラグがあってもなくても、変わったものはすべて読んで合意する。札には短い言葉だけを出し、説明は札に触れたときに出す。フラグは約束リストの項目（`flags` と、推測の中身の `guesses`）として AI が書き、どちらも合意の指紋には含めない。GUI で合意すると、合意の記録と同じコミットでフラグを外す。責任を持つのは合意した人（合意の記録の「誰が」） | |
| RV-05 | 変更・削除したものは、変更前と変更後の中身を示す（約束なら文・理由・条件・エビデンスの予定、用語と機能なら定義など、エビデンスの本体なら本文） | |
| RV-06 | 合意する（合意の記録を書き、コミットする） | |
| RV-07 | 差し戻し・コメントを書く（ストーリーの置き場所へ。レビューの指摘の記録にも残す） | |
| RV-08 | エビデンスの予定と実際の表を示す（今の `make story-evidence`） | |
| RV-09 | 約束の部分（全体・文・条件・理由・エビデンス）を指して、根拠・判断・阻害要因のどれかを書く（根拠: 調査やインタビューで分かり、判断の根拠にしたこと。判断: 合意、差し戻し、方針の決定。阻害要因: 判断できない理由と、何が分かれば判断できるか）。書いたものは下書きにため、「レビューを送る」でまとめてストーリーの置き場所に同期する。この 3 種類に当たらない AI とのやりとりは、ストーリーに残さない | RV-07 |
| RV-10 | 一覧が長いときは、まとまりごとにたたみ、たたんだ件数を示す（全体を把握しやすくするため。たたんでも RV-01 の一覧からは外さない） | RV-01 |
| RV-11 | キーボードのショートカットで、次の提案中・次の未解決の検討・前後の約束へ移る（キーは作るときに決める）。`?` で使えるキーの一覧を出す。未解決の検討の数を示す。移動のボタンは置かない | RV-09 |
| RV-12 | 約束の最後の判断が差し戻しで、その後まだ直していなければ「差し戻し中」と示す。判断の記録から出し、状態を別に記録しない | RV-09 |
| RV-13 | レビューの見方を切り替える。ブランチごと（そのブランチと、ベースブランチから分かれた点との差分）と、ストーリー全体（ストーリーの ID を持つコミットで変わったものすべての、ストーリーで最初に変える直前の中身と今の中身。ほかのストーリーが途中で同じものを変えていたら示す）。ストーリー全体の判断を記録する仕組みは作らない（漏れが見つかれば約束を足す・変え、それは提案中として審査で止まる） | RV-01 |
| RV-14 | ストーリーが前に合意したのに、今の中身にそのストーリーの合意がなくなったものを、そのストーリーの RV に「合意が外れた」として出す（ほかのストーリーの変更で外れたなら、そのストーリーの ID も示す）。ブランチごとの見方でも出す。そのストーリーのエージェントが動いていれば AG でも知らせる | RV-01、AG-02 |
| RV-15 | オラクルの定義（TLA+）のファイルが変わったら、変わった定義の読み下しの差分と、変わった定義を使う定義・約束の一覧を示す。ファイル全体を読み直させない | RV-05 |

### RP リリースの計画

約束リストに、リリースの前提や、問題が起きたときの対応を持つ項目がまだない。データの持ち方は別に決める。リリースするために必要な情報と、適切な管理の仕方についての知見がまだないので、画面の中身（版ごとのまとめ、順番の入れ替えとリリースの追加、出し方、出ている機能の一覧を含む）は、それを調べてから決める。

| 番号 | 機能 | 関係 |
|---|---|---|
| RP-01 | 機能ごとの前提（アプリの版など）と、満たされているかを示す | |
| RP-02 | 機能ごとの、リリースのための事前の準備を示す | |
| RP-03 | 機能ごとの、問題が起きたときの対応（軽微ならホットフィックス、版の切り戻し、キルスイッチなど）を示す | |

### AG エージェント

vanda は、実装する AI エージェントを tmux のセッションで起動し、待っているエージェントを tmux に 1 文を打ち込んで起こす。エージェントのセッションの終了と再開は作らない（どのストーリーでどのセッションを使うかを別に管理する必要があり、今は要らない）。

エージェントの状態（ストーリー・ブランチ・エージェントの設定の名前・tmux のセッションの結びつき、状態、活動、待っている質問）は、vanda の手元のデータの置き場所（例: `~/.local/share/vanda/`）に、リポジトリごとの小さな DB として持つ。人ごと・マシンごとの状態で、チームで共有しないので、リポジトリには入れない。

| 番号 | 機能 | 関係 |
|---|---|---|
| AG-01 | ストーリーごとに、エージェントの状態を示す（作業中 / 待機中（理由: レビュー待ち・質問への回答待ち・入力待ち（コンソール））/ 止まった / 終わった） | |
| AG-02 | 待機中になったら、ブラウザの通知と通知音で知らせる。どの画面にいても、待機中の数が分かる | |
| AG-03 | 質問（阻害要因）に答える。答えると、vanda がエージェントを起こす。RV の画面からも答えられる | RV-09、MCP-02 |
| AG-04 | 最後の活動の時刻と、今使っている道具を示す（フックから） | |
| AG-05 | エージェントを中断する（コンソールで Esc を押すのに当たる。tmux に Esc を送る）。セッションは残る | CMD-09 |

| 番号 | 機能 | 関係 |

| CMD-01 | 今効いている設定と、つながり（ストーリーの置き場所や結果を取ってくる元に、認証が通るか）を確かめる。設定を見るための画面は作らない | |

| CMD-04 | GUI を起動する | CM-01 |

| 番号 | 機能 | 関係 |
|---|---|---|
| MCP-01 | 次の仕事を受け取る。待つもの（レビュー、質問への回答）があれば、待機の理由を返す。返されたエージェントはターンを終え、vanda に起こされるのを待つ | AG-01 |
| MCP-02 | 人に質問する。質問は阻害要因として GUI に出る。答えが来るまで待つ | AG-03、RV-09 |
| MCP-03 | 懸念を出す。人が判断するまで待機になる | RV-09 |
| MCP-04 | レビューを頼む（案の約束を書き終えたことを知らせ、レビュー待ちに入る） | RV |

エージェントがコンソールで人に聞いてしまったときに備え、Claude Code のフック（入力待ち、活動、ターンの終わり、セッションの終わり）を vanda に送らせ、入力待ちを検知する（AG-01）。

#### アノテーション

`.vanda/` の外にあり、版が上がっても書き方を変えない（v1.0.0 から）。

| 書き方 | 付ける所 | 意味 |
|---|---|---|
| `@vanda:term <ID>` | 仕様の型の宣言 | この宣言は、この用語を表す |
| `@vanda:feature <ID>` | 仕様の操作の宣言 | この宣言は、この機能を表す |
| `@vanda:claim <ID>` | 仕様の宣言（性質、不変条件など） | この宣言は、この約束を表す |
| `@vanda:internal <理由>` | 仕様の型の宣言 | 仕様の中だけで使う型 |
| `@vanda:evidence <ID>` | テスト、シナリオ | これは、この約束のエビデンス |
| `@vanda:sensor <ID>` | 本番のコードの関数 | この関数は、この約束のセンサー |

- 言語を問わず、コメント（`//`、`#`、TLA+ の `\*` など）の中の `@vanda:` を探す
- 1 つのアノテーションに書く ID は 1 つ。複数の約束に関わるなら、行を分けて書く
- 読むファイルは、設定（`.vanda/config.toml`）にパターンで並べる
- アノテーションが付いているもの（テストの関数、シナリオのファイル、TLA+ の定義など）の名前は、言語ごとのアダプタが読み取る。名前は、GUI に出すことと、実行の結果をエビデンスに結びつけることに使う
- 読むファイルのパターンに当たったのに、使うアダプタが決まっていないファイルがあれば、審査で止める

#### 合意の記録

合意は、対象の鍵と中身の指紋の組に対して、誰が・いつ・どのストーリーで合意したかを記録する。「誰が」は、合意したときの git の `user.name` と `user.email`。今の中身の指紋に合う合意が 1 つでもあれば合意済。指紋の合わない合意は、消さずに履歴として残す。

| 対象 | 鍵 | 指紋を作る元 |
|---|---|---|
| 約束 | 約束の ID | 約束リストの項目から `flags` と `guesses` を除いたもの |
| 用語 | 用語の ID | 名前、定義、「〜の一部」 |
| 機能 | 機能の ID | 名前、定義、`core`・`formal`、形式手法を使わない理由 |
| シナリオ | ファイルの中身の指紋（場所は、合意したときの記録として残す） | ファイルの中身 |
| ガードレールの定義 | 取り出した定義の中身の指紋（同上） | 今効いている定義を、アダプタが取り出したもの。DB なら、空の DB にマイグレーションを全部当てた結果の構造（本番の DB からは取り出さない）。今の構造の全体を書いたファイルを持つプロジェクトでは、それを読むだけのアダプタにする |
| オラクルの定義（TLA+） | ファイルの中身の指紋（同上） | ファイルの中身全体（補助の定義の変更も、必ず合意し直しになるように） |

- ファイルは中身の指紋で合意を探すので、名前を変えただけなら合意済のまま（RV-01 には「名前の変更」として出す）。TLA+ はファイルとモジュールの名前が一致する決まりなので、名前を変えると中身も変わり、合意し直しになる
- 約束・用語・機能の ID を変えたら、新しいものとみなし、合意し直す（ID はそのものを見分ける名前のため）
- 約束リストの項目の指紋は、読み込んだ中身から作る。項目の順や空白など、書き方だけの違いでは変わらない
- 読み下しは定義ごとに持ち、変わった定義の分だけ作り直す（作り直すと、変わっていない定義の言い回しまで変わり、差分が広がるため）
- TLA+ のファイルの分け方（機能ごとのモジュールにするかなど）は、プロジェクトの規則で決める

#### 実行の結果

| 項目 | 必ずか |
|---|---|
| エビデンスの名前（アダプタが読み取った名前） | 必ず |
| 合格・不合格・飛ばした（飛ばしたものは不合格と同じに扱う） | 必ず |
| 日時 | 必ず |
| 版（コミット） | 必ず |
| 実行した環境（CI、本番の監視など） | 必ず |
| かかった時間 | あってもよい |
| 添付 | あってもよい |

添付は、実行の結果に付ける汎用の仕組み。1 件ごとに次を持つ。

| 項目 | 中身 |
|---|---|
| 名前 | その結果の中で重ならない名前。添付を名前で参照する（例: `trace-seed-1`、`trace-seed-2`） |
| 種類 | 見せ方を決める。vanda が決めた種類（`log`、`failure`、`trace`、`model-check-stats`、`input-stats`、`decoy-report`、`guardrail-trials` など）は、決めた形で書けば GUI が専用の見せ方をする。それ以外は、ふつうの添付として見せる |
| 中身の形 | JSON、テキスト、画像など |
| 中身 | 中身そのものか、中身へのリンクのどちらか（制限のある環境では、リンクだけにできる） |

- 名前と種類を分けるので、同じ種類の添付を複数付けられる（例: トレースを複数）
- 実行の記録（種類 `trace`）の形: 1 つの `trace` は、種（シード値）と操作の列の一覧を持つ。1 本の操作の列は、列の番号、終わり方（成功・エラー・食い違い）、操作の一覧を持つ。1 つの操作は、操作の名前、入力の値、オラクルの結果、実装の結果、一致したかを持つ。ランダムチェックでは、オラクルの結果の代わりに、性質を満たしたかを持つ。値はそのまま書き、長い値の省略は GUI の側で行う。細かい項目の名前は、vanda を作るときに決める
- 実行の結果と添付の保管の期間は、vanda では決めず、取ってくる元（CI の成果物、ファイルサーバーなど）の設定に任せる。vanda は、今の版の最新の結果があることだけを求め、古い結果が消えていても困らないようにする
- vanda が決めた種類と、その中身の形は、`.vanda/` の外の取り決めなので、v1.0.0 からは変えない

#### 制限のある環境の実行の結果

本番の DB との一致のように、開発者が入れない環境で動かすエビデンス（運用のステージの監視など）は、その環境の側の人や仕組みが動かし、結果を取ってくる元（CM-04）に置く。リポジトリには書き込まない。

- 実行の結果で vanda が必ず求めるのは、合格か不合格か、日時、版だけ。ログや食い違いの中身は、なくても扱える
- 食い違いの中身やログは、その環境の側に置く。結果には、その環境の側の仕組みへのリンクだけを入れてよい（開くには、その環境の権限が要る）
- 何を渡すかは、結果を作る環境の側の人（管理者）が決める
- 開発者の手元の vanda に届くのは、開発者がもともと知っている合意した中身と、その環境が一致しているかの判定だけになる

#### ストーリーの記録

根拠・判断・阻害要因（RV-09）は、ストーリーの置き場所に、人が読む本文と機械が読む情報を 1 つのコメントにして書く。

- vanda は、1 つの記録から両方を作る。正は機械が読む情報で、本文はそこから作った表示とみなす
- 機械が読む情報には、種類、対象の ID と部分、ストーリーの ID、vanda の記録の ID、本文の指紋を入れる
- 読み戻すときに本文の指紋が合わなければ、「置き場所の上で書き換えられた」と GUI に出す。人が、vanda で記録し直すか、元に戻すかを選ぶ。記録が見つからなくなったら、そのことを GUI に出す
- 埋め込み方は、置き場所のアダプタが決める。GitHub Issues 以外（Jira、Backlog、Redmine など）にも、アダプタを足して使える
- 置き場所を乗り換えるときは、前の置き場所のアダプタで記録を読み戻し、新しい置き場所のアダプタで書き直せるようにする

#### 設定

`.vanda/config.toml` に書くもの:

| 区分 | 項目 |
|---|---|
| 版 | `version`（使う vanda の版） |
| ファイル | 約束リストと合意の記録の、読むファイルやパターン |
| レイヤー | レイヤーの一覧（ID、名前、説明） |
| アノテーション | 読むファイルのパターンと、使うアダプタ |
| ガードレール | 定義の取り出しのアダプタ |
| ストーリー | 置き場所のアダプタと、その引数。コミットのメッセージの中の ID の書き方は、アダプタが既定を出し、違う書き方をしたいときだけ書く |
| 実行の結果 | 取ってくる元（環境ごとに複数）と、そのアダプタ。結果の変換のアダプタ（テストを動かす道具ごと） |
| GUI | 開いたときのベースブランチ |
| エージェント | 名前付きのエージェントの設定を、いくつでも書く。それぞれに、使うエージェントのアダプタ、起動のコマンド、引数、環境の変数、モデルなど。起動するときに名前を選ぶ（例: `vanda agent start --story 24 --agent codex`）。どの場面でどれを使うかは、プロジェクトの規則で決める |

`.vanda/checks/<名前>.toml` に書くもの: 行う審査を行う順に並べ、審査ごとに範囲（全部か、1 つのストーリーで変わったものか）を書く。

設定に書かないもの: 認証の鍵（環境の変数や、すでにある道具の認証を使う）、合意する人の名前（git の `user.name`・`user.email`）、通知の音などの人ごとの好み（GUI の側で持つ）。

環境の変数は、GUI とエージェントが起動したときのものが使われ、後から変えても効かない（変えたら起動し直す）。認証は、使うたびに読めるもの（`gh` のログインなど）をできるだけ使う。GUI でも、今どの設定で動いているかを CMD-01 と同じく確かめられるようにする。

#### アダプタ

5 種類のアダプタを、同じ作りで用意する。

| アダプタ | 受け取るもの | 返すもの |
|---|---|---|
| アノテーションの読み取り | ファイルの場所 | アノテーションごとの、付いているものの名前（JSON） |
| 実行の結果の変換（CMD-02） | テストを動かす道具の出力（`go test -json`、JUnit の XML など） | vanda の形の実行の結果 |
| ガードレールの定義の取り出し | プロジェクト（マイグレーションなど） | 今効いている定義（DB なら、空の DB にマイグレーションを当てた結果の構造） |
| ストーリーの置き場所（CM-08） | ストーリーの ID、書く記録 | ストーリーの題・本文・コメント・添付ファイル、読み戻した記録。記録を人が読む本文と機械が読む情報にして、置き場所に書く・読み戻す（埋め込み方は置き場所ごとに決める。GitHub なら HTML のコメント） |
| エージェント（CMD-06） | エージェントの設定 | エージェントの種類（Claude Code、Codex など）ごとの違いを吸収する。MCP とフックの渡し方、起こすときに打ち込む文、中断のキー |

- アダプタは外部のコマンドで、どの言語で書いてもよい。利用者が作れる
- 設定（`.vanda/config.toml`）で、ファイルのパターンや道具ごとに、使うアダプタを決める
- vanda は、quenta で使うもの（Go、シナリオ（`.txtar`）、TLA+、`go test -json`、TLC の出力）のアダプタを中に持つ
- アダプタとの受け渡しの形は `.vanda/` の外の取り決めなので、v1.0.0 からは変えない

#### エビデンスのタイプ

約束リストのエビデンスの `type` に書く値。一覧は vanda が決める。値は、日本語の言葉をそのまま英語にし、単語を `-` でつなぐ。

| タイプ | 値 | 確かめること | 実行できるか |
|---|---|---|---|
| モデル検査 | `model-check` | 決めた範囲の中のすべての状態をたどって、性質が成り立つ（TLC） | できる |
| 証明 | `proof` | すべての値で、性質が成り立つ（Dafny） | できる |
| クロスチェック | `cross-check` | オラクルと実装に同じ操作を送り、結果を比べる | できる |
| ランダムチェック | `random-check` | 無作為な入力で、性質を確かめる | できる |
| シナリオテスト | `scenario-test` | シナリオ（CLI のコマンドの並びの台本）を動かして確かめる | できる |
| 単体テスト | `unit-test` | — | できる |
| インターフェースのテスト | `interface-test` | DB や CLI などの境界の振る舞い。どのレイヤーかは、エビデンスのレイヤーで表す | できる |
| 同時実行のテスト | `concurrency-test` | — | できる |
| ガードレール | `guardrail` | 拒むべきものを試し、拒まれる | できる |
| センサー | `sensor` | 実装の中で事後条件を確かめる | — |
| 監視 | `monitoring` | 動いているものを見張る | — |
| 人のレビュー | `human-review` | 人が読んで確かめる | — |

#### 審査の種類（CMD-10）

自然言語だけの約束どうしの矛盾は、審査の種類に入れない。AI の点検は結果が揺れ、誤った指摘で止まると直すものがないため。合流の前に AI に点検させ、見つけたものを阻害要因として人に出す。

審査は、どれも失敗したら止める（「知らせるだけ」の段は設けない）。どの審査も、失敗したら直せる形にする。実行しない審査は、設定のファイルに書かない。

| 区分 | 審査 | 範囲 |
|---|---|---|
| 約束リストの形 | 読める（TOML の誤りがない）。決まった表と項目だけがあり、必須の項目がある。ステージとタイプが決まった語の中にある | 全部 |
| 約束リストの形 | ID の形が決まりどおりで、重ならない | 全部 |
| 約束リストの形 | 「〜の一部」（`part_of`）の先が用語としてあり、循環していない。約束の対象（`subjects`）が約束リストにある | 全部 |
| アノテーションのつながり | 仕様・テスト・本番のコードのアノテーションが指す ID が、約束リストにある | 全部 |
| アノテーションのつながり | 仕様の型には、用語のアノテーションか「仕様の中だけで使う」アノテーションがある。型に機能のアノテーションを付けていない | 全部 |
| 由来 | 約束リストを変えたコミットに、ストーリーの ID がある | 比べる元から後のコミット（例: このブランチで足したコミット）。履歴を書き換えないと直せない古いコミットは見ない |
| 合意 | 今の中身がすべて合意済である（提案中のものがない。前の合意から変わったものは提案中に含まれる）。範囲を 1 つのストーリーにしたときは、そのストーリーが前に合意したのに、今の中身にそのストーリーの合意がないもの（誰が変えたかを問わない）も含め、そのストーリーが今の中身に合意し直すまで止める（RV-14）。フラグ（AI 案・推測）が残っていない（合意すると外れるので、残っているのは、合意の後にフラグだけが立てられたものか、合意を通さずに書き換えられたもの） | 全部か、1 つのストーリーで変わったもの |
| 合意 | 合意の記録が、約束リストにない約束を指していない | 全部 |
| エビデンス | 予定したエビデンスが揃い、実行できるもの（テスト、シナリオ、オラクルの検査、ガードレールの試し）は、今の版での実行の結果があって合格している。結果がないものは不合格と同じに扱う。実行しないもの（人のレビュー、監視など）は、予定したもの（読むファイルなど）がある | 全部か、1 つのストーリーで変わったもの |
| キャッチしない理由 | キャッチしないデコイのそれぞれに、理由の種類と理由の文がある | 全部 |
| モデル検査 | モデル検査（TLC）が通り、どの動作も一度は起きる（矛盾した約束による空振りを見つける）。並行するストーリーの矛盾を見つけるには、合流した後の状態で動かす（どの状態で動かすかは CI の設定で決める） | 全部 |
