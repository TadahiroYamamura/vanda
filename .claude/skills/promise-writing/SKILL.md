# 約束リストの書き方

約束リストは、ソフトウェアの正とする一覧。PO はソースコードを読まず、約束リストの文を読んで合意する。PO が読んで誤解しない文にする。

## 用語・機能・約束の役割

| 種類 | 書くこと | 書かないこと |
|---|---|---|
| 用語 | それが何か（ものや概念の意味）。意味を決めるのに要る区別（例: 誤りとエラーの違い） | 振る舞い、作り方、決まり |
| 機能 | 利用者が行う操作が何か | どんな種類があるかの一覧、細かい振る舞い |
| 約束 | 振る舞い、作り方、決まり。1 件に 1 つ | |

- 種類の一覧は、用語の `part_of` で表す（例: 審査の種類は、用語「審査」の一部として並べる）
- 用語や機能の定義から振る舞いを外すときは、その振る舞いを書いた約束があることを確かめる。なければ約束を足す。どこにも書かれなくなるものを作らない

## 名前と ID

- 機能の名前は、動詞の形にする（例: 「審査を行う」。「審査」ではない）
- 機能の ID は「動詞-名詞」の形にする（例: `run-checks`、`show-claim-origin`）
- ID は、用語・機能・約束のあいだで重ならないようにする（例: 審査の agreement は、用語「合意」の `agreement` と重なるので `agreement-check`）

## 何を約束にするか

- 守らせたい振る舞いは、すべて約束に書く。書いていない振る舞いは、たまたまそうなったとみなされ、守らなくてよいものになる
- 関知しないこと（どちらでもよいこと）は書かない。書くと、将来の直しを縛る
- 細かい場面の振る舞いは、守りたい大きな性質（約束）から決める。合意の判定のように TLA+ のモデルがあるものは、TLC で反例を探して決め、PO に 1 つずつ聞かない。PO に聞くのは、大きな性質どうしがぶつかるときと、大きな性質で決まらないときだけ

## 理由（rationale）

- そうする理由を書く。仕組みの言い換え（「〜で探すため」）は理由にならない
- PO が決めたことは、PO が述べた理由を書く。「PO の決定」のような、誰が決めたかの印は書かない。後から読む人に要るのは、約束リストに書かれて合意されているという事実と、理由の中身

## 言葉

- 約束リストで定義した用語を使う。定義のない語を使いたくなったら、先に用語を足す
- 用語の区別を守る。例:
  - 誤り: 人が書いたものの間違い。エラー: 処理を続けられない失敗
  - カスタムアダプタ、vanda サーバー、ソフトウェア
- 動詞の連用形を名詞にしない（「作るかの確かめ」ではなく「作るかどうかを確かめる問い」。「合意し直しにする」ではなく「合意し直すことを求める」）
- 1 文に条件を詰めない。条件が 2 つを超えたら、句点で区切る
- 消えた文書への参照（昔の仕様の番号など）を書かない

## フラグ

- AI が書いた約束・用語・機能には `flags = ["ai-proposal"]` を付ける
- コードや文書から推し量って書いた所には、`guesses` に何を推し量ったかを書く

## 書いた後

- `vanda check` の promise-list-shape が「通った」になることを確かめてからコミットする。TOML の文字列の中の `\` は `\\` と書く
- コミットのメッセージの末尾に `Story: <ストーリーの ID>` のトレーラーを書く。Co-Authored-By などのトレーラーと、空行をはさまず同じ段落にする
- 直した約束の ID と、PO が合意のときに見るべき所（自分で決めたこと）を報告する
