# 約束リストの書き方

約束リストは、ソフトウェアについて正とする一覧。PO はソースコードを読まず、約束リストの文を読んで承認する。PO が読んで誤解しない文にする。

## 用語・機能・約束の役割

| 種類 | 書くこと | 書かないこと |
|---|---|---|
| 用語 | それが何か（ものや概念の意味）。意味を決めるのに要る区別（例: 誤りとエラーの違い） | 振る舞い、作り方、決まり |
| 機能 | 約束を実現するために実装するもの（`.claude/rules/promises.md`） | 実現する約束を言えないもの、ほかの機能の部品（画面の部品、表示の細部） |
| 約束 | 振る舞い、作り方、決まり。1 件に 1 つ | |

- 種類の一覧は、用語の `part_of` で表す（例: チェックの種類は、用語「チェック」の一部として並べる）
- 用語や機能の定義から振る舞いを外すときは、その振る舞いを書いた約束があることを確かめる。なければ約束を足す。定義から外したせいで、どこにも書かれない振る舞いを出さない

## 名前と ID

- 機能の名前は、動詞の形にする（例: 「承認を取り消す」。「承認の取り消し」ではない）
- 機能の ID は「動詞-名詞」の形にする（例: `run-checks`、`show-claim-origin`）
- 機能の名前を、用語の名前に「する」を付けただけの形にしない（例: 「承認する」ではなく「レビューで承認する」）。文の中のふつうの動詞と同じ字になり、参照に書き換える時に、用語を指す所が機能を指してしまう。コマンドの名前を括弧で添えて字がずれるもの（「チェックする（vanda check）」）は、まぎれないのでよい
- 文の中で動詞として使う時は、用語を参照して「する」を続ける（`{@id:agreement}する`）。機能を参照するのは、その操作を名指しする時だけにする
- ID は、用語・機能・約束のあいだで重ならないようにする（例: チェックの agreement は、用語「承認」の `agreement` と重なるので `agreement-check` にする）

## 何を約束にするか

- 何を約束にするか・しないかの基準は `.claude/rules/promises.md` に従う
- 関知しないこと（どちらでもよいこと）は書かない。書くと、将来直すときの縛りになる
- 細かい場面の振る舞いは、守りたい大きな性質（約束）から決める。承認の判定のように TLA+ のモデルがあるものは、PO に 1 つずつ聞かず、TLC で反例を探して決める。PO に聞くのは、大きな性質どうしがぶつかるときと、大きな性質から決まらないときだけ

## 理由（rationale）

- そうする理由を書く。仕組みの言い換え（「〜で探すため」）は理由にならない
- PO が決めたことには、PO が述べた理由を書く。「PO の決定」のような、誰が決めたかの印は書かない。後から読む人に要るのは、約束リストに書かれて承認されているという事実と、理由の中身

## 言葉

- 約束リストで定義した用語を使う。定義のない語を使いたくなったら、先に用語を足す
- 用語の区別を守る。例:
  - 誤り: 人が書いたものの間違い。エラー: 処理を続けられない失敗
  - カスタムアダプタ、vanda サーバー、ソフトウェア
- 動詞の連用形を名詞にしない（「作るかの確かめ」ではなく「作るかどうかを確かめる問い」。「承認し直しにする」ではなく「承認し直すことを求める」）
- 1 文に条件を詰めない。条件が 2 つを超えたら、句点で区切る
- 消えた文書への参照（昔の仕様の番号など）を書かない

## 参照

- 名前を除く、自然言語で書く項目（用語・機能の definition、約束の statement・rationale・condition・guesses・model_check_waiver など）で、ほかの用語・機能・約束を指す時は、名前を文字のまま書かず、`{@id:<ID>}` と書く。画面では、用語と機能は名前に、約束は ID に置き換えて出す
- 用語・機能の名前が、その意味でなく、ほかの語の一部やふつうの言葉として出てくる時は、参照にしない（例: `vanda check` の vanda、標準エラーのエラー）
- かぎかっこで囲んだ、画面や CLI にそのまま出す文言の中は、参照にしない。参照にすると、用語の名前を変えた時に、約束の文言だけが変わってしまう（用語「チェック」のように用語を名指しする形は除く）
- 文字の `{@` は `{@@` と書く
- 参照の文は、置き換えた後の文として読めるように書く（参照の前後の助詞を、名前に続けて読んで不自然にしない）
- 文字のまま書いた名前をまとめて参照に書き換える時は、付属の `refs.py` を使う
  1. `python3 refs.py candidates .vanda/promises.toml` で、名前を長い順に当てた候補を出す
  2. 候補ごとに、その語がその用語・機能を指しているかを haiku に判定させる（1 回に 20 件ほど。1 回ごとに新しいエージェントにする。入力は、文・語・その用語の定義だけにする）
  3. 「いいえ」「迷った」と、まぎれやすい名前の「はい」を、親が見直して採るものを決める
  4. 外した候補があれば、`python3 refs.py candidates .vanda/promises.toml <外した候補>` で当て直し、新しく出た候補も 2・3 で決める（端が重なる名前は、長いほうに隠れて最初は候補に出ない）
  5. 書き換えの後の差分を、haiku とは別のモデル（sonnet と opus）にも見直させ、間違った参照を挙げさせる
  6. `python3 refs.py apply .vanda/promises.toml <採る候補>` で書き換え、`python3 refs.py verify <前> <後>` で、参照を名前に置き換えた文が書き換えの前と同じかを確かめる

## フラグ

- AI が書いた約束・用語・機能には `flags = ["ai-proposal"]` を付ける
- コードや文書から推し量って書いた所には、`guesses` に何を推し量ったかを書く

## 書いた後

- 書いた文の日本語を、別のエージェントに確かめさせる
  - 書いた本人は、言いたいことを知っているので、抜けた主語や不自然な言い回しを補って読んでしまう。そのため、文脈を持たないエージェントに読ませる
  - 確かめ役には、モデルに haiku を指定する。範囲を狭めれば haiku でも不自然な所をよく見つけるので、渡すのは差分の文だけにする（`git diff -U0 .vanda/promises.toml` で変わった文）
  - 確かめ役には、文ごとに「日本語として不自然な所があるか」と「どの箇所か、何が不自然か」だけを答えさせる
  - 確かめ役の指摘を採るかは、書いた本人が決める。確かめ役は用語の定義を知らないので、定義した用語（承認済、失効した承認 など）を言い換える案や、意味を変える案を出すことがある。採らなかった指摘は報告しない
- `vanda check` の promise-list-shape が「通った」になることを確かめてからコミットする。TOML の文字列の中の `\` は `\\` と書く
- コミットメッセージの末尾に `Story: <ストーリーの ID>` のトレーラーを書く。このトレーラーは、Co-Authored-By などのほかのトレーラーと空行をはさまず、同じ段落に書く
- 直した約束の ID と、PO が承認するときに見るべき所（自分で決めたこと）を報告する
