# ストーリーの書き方

## ストーリーと課題

課題は解決したい問題や懸念。ストーリーは課題を解決するために何を作るかを書いたもの。
ストーリーには次の4つすべてを書かなくてはならない（分からない項目は PO に聞く）。
ストーリーと課題は印（ラベルなど）を付けて PO が管理しやすくする（ストーリーには `story`、課題には `problem` をつける）。

| 項目 | 書くこと |
|---|---|
| 誰のため | 誰がそれを望むか（役割） |
| なぜ | その人に何の得があるか。これがないと価値があるか、もっと良いやり方がないかを判断できない |
| どんな機能 | その人に何ができるようになるか、何が変わるか |
| 終了条件 | 何が達成できれば終わったといえるか。読んだ人が終わったかどうかを確かめられる文で書く |

## 本文と添付

ストーリーは、現場の人（エンドユーザー。エンジニアとは限らない）と開発者が読む。

- 本文は、現場の人が読んで合意できる言葉で書く。開発の言葉（ファイル名、関数名、内部の用語）を入れない
- 開発者が作り始めるのに要る情報（制約、影響範囲、関連する決定）は、ストーリー本文ではなく添付文書として書く
- 後から「どういう経緯で作ったか」が分かるよう、前提となる制約と要求を「背景」に書く

## 本文の形

```markdown
## 誰のため

## なぜ

## どんな機能

## 終了条件

## 解決する課題

## 背景

## 決めること

## 進め方
```

- 「解決する課題」「背景」「決めること」「進め方」は、あるときだけ書く
- 「決めること」は、議題と決定の表にする。決まっていない議題は、決定を空にする。決まっても、行を別の節に移さない

```markdown
## 決めること

| 議題 | 決定 |
|---|---|
| テーマ | Material for MkDocs を使う |
| 載せる中身 | |
```

## 書いた後

- 次に当てはまるものがあれば報告する: ほかのストーリーが終わらないと始められない、話し合いで変えられる余地がない、得が書かれていない、見積もれない、大きすぎるから分割すべきである、終了条件を確かめられない
- 書いた・直したストーリーの URL を報告する
