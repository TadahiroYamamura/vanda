# エビデンスの予定の選び方

1 つの約束に、穴の位置が違う層を重ねる（スイスチーズモデル）。書くのも動かすのも安い層は厚く重ね、高い層は見合う所に使う。今あるテストに合わせて予定を決めない。予定に合うテストがなければ、テストを足す。

| タイプ | 使う場面 |
|---|---|
| `unit-test` | どの振る舞いにも使う既定の層。分岐、計算、形の検査 |
| `random-check` | 入力の範囲が広く、性質として書ける約束（例: ID は重ならない） |
| `model-check` | 状態が変わり、操作の順番で結果が変わるもの（例: 承認・取り消し・変更）。状態の数を小さく保てる範囲で使う |
| `cross-check` | `model-check` を書いた約束で、実装がモデルと同じに動くことを確かめる |
| `scenario-test` | 利用者の操作の流れ（CLI は txtar、端末で質問するものは Expect、画面は E2E）。単体で確かめた振る舞いをつないでも壊れないことを見る。1 つの機能につき、主な流れを書く |
| `interface-test` | 境界での振る舞い（端末、HTTP、ファイル、外の API） |
| `concurrency-test` | 同時に動くものがある所 |
| `guardrail` | データを壊すもの（約束リストや承認の記録の書き換えなど）を拒む |
| `sensor` | `guardrail` で防ぎきれないものを、動いている最中に見つける（事後条件） |
| `human-review` | 機械では確かめられないもの（見た目、言葉づかい） |

- データを壊しうる約束には、`unit-test`・`guardrail`・`sensor` を重ねる
- `sensor` には、約束を破る状態をわざと作り、センサーが知らせることを確かめるテストを組にする。テストの側から破れないものは、事後条件を破るように壊したデコイで確かめる。印（`@vanda:sensor`）だけでは、センサーが働くことは分からない
