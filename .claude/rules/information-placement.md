# 情報の置き場所

情報は、その情報が正しくあり続ける期間と同じ寿命の場所に置く。調べる人は「コード → git blame → コミット → Issue・約束リスト」の順にたどるので、コミットのメッセージはほかの置き場所への中継点になる。

vanda は vanda で開発する。作ったものが何をするかの正（オラクル）は、約束リストにある。

| 置き場所 | 寿命 | 置く情報 |
|---|---|---|
| コード | 今 | 何をどうしているか |
| テスト | 今 | 期待する振る舞いの具体例 |
| コメント | そのコードがある間 | このコードがこの形である理由（制約、選ばなかった案、直感に反する点） |
| 約束リスト（`.vanda/promises.toml`） | 置き換えられるまで | 作ったものの用語・機能・振る舞いと、その理由（PO の決定を含む）・条件・エビデンスの予定 |
| 合意の記録（`.vanda/agreements.toml`） | その時点で固定 | PO がどの約束に合意したか（vanda が書く） |
| `docs/spec.md` | 作るまで | まだ作っていない機能と、その範囲 |
| `docs/formats.md` | 置き換えられるまで | 外の人（アダプタを作る人など）が読む、ファイル・アノテーション・CLI・API の取り決めの説明 |
| `docs/plans/` | その作業の間 | 開発者とテスト担当に渡す、作り方とテストの計画 |
| `docs/pitfalls.jsonl` | その構造がある間 | 間違えても気づきにくい構造（`.claude/rules/pitfalls.md`） |
| `.claude/rules/` | 置き換えられるまで | いつも守る書き方の決まり |
| コミットのメッセージ | その時点で固定 | なぜこの変更をこのときに入れたか |
| GitHub Issues | その時点で固定 | ストーリー（解決したいこと、背景）、決めること、今後の課題 |

- コードがある限り正しい理由 → コメント
- 振る舞いがそうである理由（PO の決定を含む） → 約束の `rationale`
- 変えた時点の事情（きっかけ、移る途中、消した・置き換えた理由） → コミットのメッセージ
- 分かっている懸念・今後の課題 → Issue か TODO のコメント（コミットのメッセージに書くと、blame しない限り見つからない）
- 振る舞い・用語が変わったら、コードと同じコミットで約束リストを直す。外の人が読む取り決めが変わったら、同じコミットで `docs/formats.md` も直す
- `docs/spec.md` の機能を作ったら、約束リストに書き、`docs/spec.md` から消す
- 約束リストと `docs/` が食い違ったら、約束リストを正とし、`docs/` を直す
- モジュールをまたぐ、戻しにくい決定の記録（ADR）の置き場所は、まだない。要るときは、作る前に監督に聞く
