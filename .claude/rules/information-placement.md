# 情報の置き場所

情報は、その情報が正しくあり続ける期間と同じ寿命の場所に置く。調べる人は「コード → git blame → コミット → Issue・仕様」の順にたどるので、コミットのメッセージはほかの置き場所への中継点になる。

| 置き場所 | 寿命 | 置く情報 |
|---|---|---|
| コード | 今 | 何をどうしているか |
| テスト | 今 | 期待する振る舞いの具体例 |
| コメント | そのコードがある間 | このコードがこの形である理由（制約、選ばなかった案、直感に反する点） |
| `docs/spec.md` | 置き換えられるまで | 何を作るか（機能と、その範囲） |
| `docs/formats.md` | 置き換えられるまで | ファイル・アノテーション・CLI・API の形（利用者や画面が頼る取り決め） |
| `docs/terms.md` | 置き換えられるまで | 言葉の意味 |
| `docs/plans/` | その作業の間 | 開発者とテスト担当に渡す、作り方とテストの計画 |
| `docs/pitfalls.jsonl` | その構造がある間 | 間違えても気づきにくい構造（`.claude/rules/pitfalls.md`） |
| `.claude/rules/` | 置き換えられるまで | いつも守る書き方の決まり |
| コミットのメッセージ | その時点で固定 | なぜこの変更をこのときに入れたか |
| GitHub Issues | その時点で固定 | 解決したいこと、背景、決めること、今後の課題 |

- コードがある限り正しい理由 → コメント
- 変えた時点の事情（きっかけ、移る途中、消した・置き換えた理由、PO の決定） → コミットのメッセージ
- 分かっている懸念・今後の課題 → Issue か TODO のコメント（コミットのメッセージに書くと、blame しない限り見つからない）
- 仕様・形・言葉が変わったら、コードと同じコミットで `docs/` を直す
- モジュールをまたぐ、戻しにくい決定の記録（ADR）の置き場所は、まだない。要るときは、作る前に監督に聞く
